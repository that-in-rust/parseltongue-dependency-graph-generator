  ## Part 1: The Five Integration Patterns                                                                                                                              
  ### Pattern 1: Direct rustc_private (30+ tools)                                                                                                                       
  The most common pattern - directly using `#![feature(rustc_private)]` and depending on `rustc_*` crates.                                                              
  **Entry point:** `rustc_driver::Callbacks`                                                                                                                            
  **Hook point:** `after_analysis` callback provides `TyCtxt<'tcx>`                                                                                                     
  ```rust                                                                                                                                                               
  #![feature(rustc_private)]                                                                                                                                            
  extern crate rustc_driver;                                                                                                                                            
  struct MyCallbacks;                                                                                                                                                   
  impl rustc_driver::Callbacks for MyCallbacks {                                                                                                                        
      fn after_analysis<'tcx>(                                                                                                                                          
          &mut self,                                                                                                                                                    
          _compiler: &Compiler,                                                                                                                                         
          tcx: TyCtxt<'tcx>                                                                                                                                             
      ) -> Compilation {                                                                                                                                                
          // Full access to MIR, HIR, types, traits                                                                                                                     
          Compilation::Stop                                                                                                                                             
      }                                                                                                                                                                 
  }                                                                                                                                                                     
  ```                                                                                                                                                                   
  **Pros:** Maximum power, access to everything                                                                                                                         
  **Cons:** Nightly-only, breaks frequently, complex setup                                                                                                              
  **Users:** Kani, Miri, Creusot, Flux, Prusti, Rudra, RAPx, lockbud, rustc_codegen_*                                                                                   
  ### Pattern 2: rustc_plugin Framework (4 tools)                                                                                                                       
  Brown University's framework generalizing Clippy's pattern.                                                                                                           
  **Components:**                                                                                                                                                       
  - `rustc_plugin`: Cargo integration, CLI scaffolding                                                                                                                  
  - `rustc_utils`: Extension traits for MIR, HIR, spans                                                                                                                 
  **Users:**                                                                                                                                                            
  | Tool | Version | Nightly |                                                                                                                                          
  |------|---------|---------|                                                                                                                                          
  | Flowistry | 0.14.2 | 2025-08-20 |                                                                                                                                   
  | Aquascope | 0.12.0 | 2024-12-15 |                                                                                                                                   
  | Paralegal | 0.12.0 | 2024-12-15 |                                                                                                                                   
  | Argus | 0.14.1 | 2025-08-20 |                                                                                                                                       
  **Key benefit:** Framework handles boilerplate, you focus on analysis                                                                                                 
  ### Pattern 3: Charon/LLBC Decoupling (5+ tools)                                                                                                                      
  Charon extracts MIR to a language-agnostic JSON format (LLBC), decoupling tools from compiler entirely.                                                               
  **Pipeline:**                                                                                                                                                         
  Rust source → rustc → MIR → Charon → LLBC (JSON) → Downstream tools                                                                                                   
  | Tool | Purpose | Backend |                                                                                                                                          
  | Aeneas | Functional verification | F*, Coq, HOL4, Lean |                                                                                                            
  | Eurydice | C code generation | C compiler |                                                                                                                         
  | Kani (partial) | Model checking | CBMC via LLBC |                                                                                                                   
  | Hax | Cryptographic verification | F*, Rocq |                                                                                                                       
  **Key benefit:** Tools don't break when rustc changes                                                                                                                 
  **Trade-off:** Loss of incremental analysis, must re-extract                                                                                                          
  ### Pattern 4: Stable MIR / rustc_public (1 tool migrating)                                                                                                           
  Official rust-lang project to provide SemVer-stable MIR API.                                                                                                          
  **Architecture:** Two crates like `proc-macro2`                                                                                                                       
  - `rustc_public`: Public stable API (to be on crates.io)                                                                                                              
  - `rustc_smir`: Internal translation layer                                                                                                                            
  **Status:** v0.1 not yet published, Kani is pioneering adopter                                                                                                        
  **Key benefit:** Eventually works on stable Rust                                                                                                                      
  **Current state:** Still nightly-only, incomplete                                                                                                                     
  ### Pattern 5: No Compiler Dependency (5+ tools)                                                                                                                      
  Some tools avoid compiler internals entirely.                                                                                                                         
  | Tool | Approach |                                                                                                                                                   
  |------|----------|                                                                                                                                                   
  | cargo-scan | Uses `cargo` crate for metadata |                                                                                                                      
  | Polonius | Standalone Datalog engine |                                                                                                                              
  | cargo-semver-checks | rustdoc JSON + Trustfall |                                                                                                                    
  | cargo-modules | ra_ap_* crates |                                                                                                                                    
  | Dylint | Dynamic library loading |

  ## Part 9: Use Case Taxonomy for Parseltongue                                                                                                                         
  ### Use Case 1: "Where is X defined?"                                                                                                                                 
  **Tools that solve this:** All of them - fundamental operation                                                                                                        
  **Data needed:** HIR → DefId → Span                                                                                                                                   
  **Accuracy requirement:** 100% - must be exact                                                                                                                        
  ### Use Case 2: "What calls X?"                                                                                                                                       
  **Tools:** Flowistry, Paralegal, lockbud, RAPx                                                                                                                        
  **Data needed:** MIR call graph                                                                                                                                       
  **Accuracy requirement:** 100% - cannot miss callers                                                                                                                  
  ### Use Case 3: "What does X depend on?"                                                                                                                              
  **Tools:** Flowistry, Paralegal, cargo-scan                                                                                                                           
  **Data needed:** MIR dataflow analysis                                                                                                                                
  **Accuracy requirement:** High - missing dependencies = incomplete context                                                                                            
  ### Use Case 4: "What can go wrong here?"                                                                                                                             
  **Tools:** Kani, Miri, lockbud, Rudra, RAPx                                                                                                                           
  **Data needed:** Full semantic analysis + domain knowledge                                                                                                            
  **Accuracy requirement:** Very high for safety-critical                                                                                                               
  ### Use Case 5: "What types implement trait T?"                                                                                                                       
  **Tools:** Argus, all tools using TyCtxt                                                                                                                              
  **Data needed:** Trait solver output                                                                                                                                  
  **Accuracy requirement:** 100% - cannot miss implementations                                                                                                          
  ### Use Case 6: "What's the ownership/borrow situation?"                                                                                                              
  **Tools:** Aquascope, Miri, Flowistry                                                                                                                                 
  **Data needed:** Polonius borrowcheck facts                                                                                                                           
  **Accuracy requirement:** Very high - wrong borrow info = confusion                                                                                                   
  ### Use Case 7: "What would break if I change X?"                                                                                                                     
  **Tools:** cargo-semver-checks, Paralegal                                                                                                                             
  **Data needed:** Cross-crate references, trait impls                                                                                                                  
  **Accuracy requirement:** High - false positives are annoying                                                                                                         
  ### Use Case 8: "Is this code correct?"                                                                                                                               
  **Tools:** Kani, Prusti, Creusot, Flux                                                                                                                                
  **Data needed:** Full semantic model + specifications                                                                                                                 
  **Accuracy requirement:** Maximum - proving correctness

   - # Moment-to-Moment UX Blueprint                                                                                                                                    
  **Primary Segment:** OSS Rust Contributors, Large Repos                                                                                                               
  **Document Purpose:** Define the felt experience. Not what the system does — what the user feels.                                                                     
  ## The Core Insight                                                                                                                                                   
  > The user doesn't want "search results." They want to feel like someone who understands the codebase is sitting next to them, pointing at the right file, saying     
  "start here."                                                                                                                                                         
  Everything else is implementation.                                                                                                                                    
  ## Part 1: The Felt Journey (7 Moments)                                                                                                                               
  ### MOMENT 0: The Empty Box                                                                                                                                           
  **User sees:** Chat box, current branch indicator, repo scope badge                                                                                                   
  **User does:** Types: "How does authentication work?"                                                                                                                 
  **What happens:**                                                                                                                                                     
  - System classifies intent: `explain-architecture` (84% confidence)                                                                                                   
  - System identifies scope: 3 relevant crates, 47 candidate entities                                                                                                   
  **User feels:** "It knows where I am. I don't have to explain everything."                                                                                            
  **Critical detail:** The branch indicator matters. It says "I see your context." The repo scope badge says "I won't search outside." This reduces cognitive load      
  before the user types a single word.                                                                                                                                  
  ### MOMENT 1: The Check-In                                                                                                                                            
  **User sees:**                                                                                                                                                        
  I interpreted your intent as: Explain authentication architecture (84%)                                                                                               
  Is this right? [Yes] [No, I meant something else]                                                                                                                     
  **User does:** Accepts or corrects                                                                                                                                    
  - If accepted: Proceed to Option Cards                                                                                                                                
  - If corrected: System offers 2-3 alternatives:                                                                                                                       
    - "Find where auth is called"                                                                                                                                       
    - "Find auth implementation details"                                                                                                                                
    - "Find auth test coverage"                                                                                                                                         
  **User feels:** "I'm in control. This isn't a black box."                                                                                                             
  **Why this matters:** Every search tool skips this step. They guess and dump results. By asking, we:                                                                  
  1. Reduce wrong-path exploration                                                                                                                                      
  2. Build trust through transparency                                                                                                                                   
  3. Create a "conversation" not a "query"                                                                                                                              
  **The Shreyas Principle:** Users forgive mistakes if you acknowledge uncertainty. They don't forgive false confidence.                                                
  ### MOMENT 2: The Option Cards (The Most Critical Moment)                                                                                                             
  **User sees:** 3-5 cards, NOT a list of search results                                                                                                                
  **What makes this different from search results:**                                                                                                                    
  | Search Results | Option Cards |                                                                                                                                     
  |----------------|--------------|                                                                                                                                     
  | Ranked by keyword match | Clustered by semantic meaning |                                                                                                           
  | Show snippet | Show full context package |                                                                                                                          
  | "Here's what matched" | "Here's what you probably want" |                                                                                                           
  | User must read to compare | User can scan to compare |                                                                                                              
  | No cost information | Token cost visible upfront |                                                                                                                  
  **What each card shows:**                                                                                                                                             
  ┌─────────────────────────────────────────────────────────────┐                                                                                                       
  │ 🎯 auth::service::authenticate_user                         │                                                                                                       
  │                                                             │                                                                                                       
  │ 📍 crates/auth/src/service.rs:47-89                         │                                                                                                       
  │ 🔗 Related: login(), validate_token(), User, AuthError      │                                                                                                       
  │ ⚠️  Risk: Medium (12 callers, 3 downstream modules)          │                                                                                                       
  │ 📊 ~900 tokens | 89% match | ✅ Up to date                  │                                                                                                       
  │ Why this card?                                              │                                                                                                       
  │   • Lexical match: "authenticate" in function name          │                                                                                                       
  │   • Semantic: Central to auth flow                          │                                                                                                       
  │   • Graph: Most connected auth entity                       │                                                                                                       
  └─────────────────────────────────────────────────────────────┘                                                                                                       
  **User feels:** "I can make a decision without reading code. I understand my options."                                                                                
  **The hidden work:**                                                                                                                                                  
  - Entity extraction (`ra_ap_hir`)                                                                                                                                     
  - Graph traversal (find neighbors, calculate centrality)                                                                                                              
  - Token estimation (signature + docs + related entities)                                                                                                              
  - Freshness check (git hash comparison)                                                                                                                               
  **Why cards, not list:** A list says "here's everything we found." Cards say "here's what matters." The user doesn't want to filter. They want to choose.             
  ### MOMENT 3: The Commitment (Card Selection)                                                                                                                         
  **User sees:** Clicked card expands slightly, showing a bit more detail                                                                                               
  **User does:** Confirms this is the right target                                                                                                                      
  - System prepares high-ROI context packet                                                                                                                             
  - System pre-computes related entities for deep dive                                                                                                                  
  - System warms up blast radius calculation (just in case)                                                                                                             
  **User feels:** "Low risk to try. If I'm wrong, I can go back."                                                                                                       
  **The psychological contract:** At this moment, the user is making a bet. They're saying "I think this is it." The system must:                                       
  1. Make the bet feel small (easy to reverse)                                                                                                                          
  2. Reward the bet quickly (show value immediately)                                                                                                                    
  3. Not punish wrong bets (offer alternatives, not dead ends)

  ## Part 7: The Shreyas Principles (Applied)                                                                                                                           
  1. **Users don't want search. They want a guide.**                                                                                                                    
     - We're not building a search engine. We're building a knowledgeable colleague.                                                                                    
  2. **Show your work.**                                                                                                                                                
     - Every result includes "Why this card exists." No black boxes.                                                                                                    
  3. **Admit uncertainty.**                                                                                                                                             
     - Low confidence is shown explicitly. Users forgive uncertainty. They don't forgive false confidence.                                                              
  4. **Preserve momentum.**                                                                                                                                             
     - The journey is continuous. No reset at each step. Context accumulates.                                                                                           
  5. **Make the bet feel small.**                                                                                                                                       
     - Every choice is easy to reverse. "Back" is always available. No dead ends.                                                                                       
  6. **The user is the decision maker.**                                                                                                                                
     - We recommend. We don't decide. The user always has the final say.

  # Code Search Workflow                                                                                                                                                
  Use **intent-specific workflow variants**, not one universal flow. For OSS Rust in large repos, this is a strong segment x workflow map:                              
  | Segment | Workflow Variant | How LLM Navigates | Output |                                                                                                           
  | New contributor | `Map-first onboarding` | Query -> crate/module map -> key public APIs -> “read order” path | 30-min learning route |                              
  | Returning contributor | `Task-first patch path` | Issue text -> candidate entities -> enclosing owners -> minimal edit set | patch plan with files/lines |          
  | Core maintainer | `Blast-radius before edit` | Proposed change -> callers/callees/trait impls/SCC neighbors | risk-ranked impact report |                           
  | Reviewer | `PR truth-check` | Diff -> changed entities -> dependency + control-flow slices | review checklist + hidden break risks |                                
  | Bug fixer | `Symptom-to-path` | Error/log tokens -> likely execution paths -> dataflow checkpoints | top 3 root-cause hypotheses |                                  
  | API migrator | `Signature migration graph` | Old API refs -> wrapper/adapters -> downstream breakpoints | ordered migration sequence |                              
  | Unsafe code owner | `Soundness audit mode` | `unsafe` blocks -> aliasing/lifetime neighbors -> call paths | invariant map + violation candidates |                  
  | Perf contributor | `Hotpath context mode` | perf clue -> hot functions -> transitive callee chain + alloc points | optimization targets with confidence |           
  Top 3 to build first for your segment:                                                                                                                                
  1. `Blast-radius before edit` (maintainers feel this pain daily)                                                                                                      
  2. `PR truth-check` (review is the bottleneck in large OSS)                                                                                                           
  3. `Task-first patch path` (contributor throughput)                                                                                                                   
  Key creative variations on your current pipeline:                                                                                                                     
  1. **Auto-route by intent** before retrieval (`bug`, `refactor`, `review`, `migrate`, `unsafe`, `perf`).

     Key Insight: The "Encapsulating Public Entity" Pattern                                                                                                             
     This is the crucial observation:

     1. Public interfaces are stable - less likely to change than internals                                                                                             
     2. Public interfaces are the API boundary - what you actually interact with                                                                                        
     3. LLMs get context through the public contract, not lost in implementation details                                                                                
     4. Private code is accessed through its public interface in real usage                                                                                             
     The Pattern in Abstract Terms                                                                                                                                      
     Phase            │ Input       │ Output              │ Key Operation                                                                                               
     -----------------+-------------+---------------------+------------------------------

  ### Rust Analyzer Superset Mapping                                                                                                                                    
  Assessment:                                                                                                                                                           
  1. Rust Analyzer inputs are a practical superset of our read-pointer format.                                                                                          
  2. RA carries richer identity/range context (file identity + typed symbol context + ranges), which can be projected to our compact read key.                          
  Canonical layers:                                                                                                                                                     
  1. Stable identity layer:                                                                                                                                             
     - `language|||kind|||scope|||name|||file_path|||discriminator`                                                                                                     
  2. Read-pointer layer (for code fetch):                                                                                                                               
     - `file_path|||entity_key|||start_line|||end_line`                                                                                                                 
  Projection contract:                                                                                                                                                  
  1. Resolve RA symbol/definition to canonical `entity_key`.                                                                                                            
  2. Convert RA range/offsets to line-based span.                                                                                                                       
  3. Emit read pointer exactly as:                                                                                                                                      
     - `filepath|||entity|||StartLine|||EndLine`                                                                                                                        
  4. Use full entity span for default code read; keep narrower selection ranges optional for focused context.                                                           
  Example:                                                                                                                                                              
  1. `entity_key = rust|||fn|||auth::service|||authenticate_user|||src/auth/service.rs|||sig_v3`                                                                        
  2. `read_pointer = src/auth/service.rs|||rust|||fn|||auth::service|||authenticate_user|||src/auth/service.rs|||sig_v3|||40|||96`

     - session_reads(session_id, path, hash, read_at) — tracks what each session last saw

     2. FRESH/STALE Detection Pattern
     - Compare current file hash to last-seen hash in session
     - Same hash → FRESH (return one-line confirmation)
     - Different hash → STALE (compute and return unified diff)
     - This maps directly to our Screen 3 FRESH/STALE badge and Screen 7 staleness check

     3. Line-Based LCS Diff (src/differ.ts)
     - Longest Common Subsequence for line-level diffs
     - Returns unified diff format + exact changed line numbers
     - Could be useful for incremental re-analysis: only re-parse changed line ranges

     4. Session Isolation
     - Different sessions can be at different file versions
     - Useful if we ever need multi-user or multi-branch scenarios

     What NOT to Adopt from Cachebro

     - The caching layer itself (we don't cache file reads, we index)
     - The MCP proxy pattern (we're HTTP-first)
     - Token tracking/stats (interesting but out of scope)

     What it is: Per-project persistent memory for coding agents. Memories survive across sessions, improve through reinforcement learning (weight adjustment based on agent feedback).

     Patterns Worth Noting

     1. Turso Connection Pattern — Short-Lived Connections
     - Opens/closes DB connection per operation to avoid multi-process lock contention
     - PRAGMA busy_timeout = 5000 for concurrent access
     - Retry with exponential backoff (max 10 attempts) if DB locked
     - IMPORTANT: This is a real-world lesson about Turso embedded driver file locking

     2. Per-Project DB Pattern
     - Each project gets .memelord/memory.db — no shared state across projects
     - Exactly matches our .parseltongue/index.db per-codebase pattern

     3. Vector Search in libSQL
     - vector_distance_cos(embedding, ?) for similarity search
     - Float32 vectors stored as BLOB
     - Works well enough for small-scale (hundreds/thousands of memories)

     Entity Taxonomy: Every Possible Entity in a Codebase

     Goal

     After .gitignore filtering, exhaustively list every entity type, its kind, and its primary key format.

     Primary Key Format

     Uniform format for ALL entities: path:start_line:end_line

     Sentinel values:
     - -1:-1 → FOLDER (the path is a directory)
     - 0:0 → FILE (the path is a file, no line-level content)
     - N:M where N ≥ 1 → CODE SPAN (parsed snippet within a file)

     Examples:
     src/auth/:-1:-1                    → folder
     src/auth/service.rs:0:0            → file
     src/auth/service.rs:8:25           → code span (fn login)

     Searchability Rule

     - SEARCHABLE: Only code spans (N:M) go into FTS. These have parsed name + signature + snippet.
     - NOT SEARCHABLE: Folders and files are graph-only entities. They exist for connectivity (folder→file→code_span) and for staleness checks (file_hash), but they don't pollute search results.
     - NOT STORED: Full file content is NEVER stored. Only parsed snippets.

     ---
     The is_test Question

     test is not a separate kind — it's a flag (is_test = true) on any code span entity (usually functions). This means:
     - Test entities use the same pk format, same table, same schema
     - They differ only in the is_test column
     - Search can filter them in or out
     - Graph edges FROM tests TO production code are preserved (useful for blast radius)

     CODEMOGGER - Code Indexing Library (STEAL HEAVILY)

     What it is: Tree-sitter code chunker + Turso/libSQL store with FTS + vector search. Single .db file per codebase. 14 languages. MCP server + CLI.

     Patterns to Adopt

     1. File Walker + .gitignore (src/scan/walker.ts)
     - Hardcoded ALWAYS_IGNORE set: .git, node_modules, target, build, dist, pycache, .venv, .cargo, .rustup
     - Simplified .gitignore parsing: directory names only (no glob patterns). Practical tradeoff.
     - Skips hidden files (starts with .), empty files, files >1MB
     - Returns: absPath, relPath, language, SHA-256 hash, content

     2. SHA-256 Hash-Based Incremental Indexing (src/index.ts)
     - On reindex: compute hash per file, compare to stored hash
     - Changed → re-chunk + re-embed. Unchanged → skip.
     - 5-phase pipeline: scan → hash check → chunk+write → embed → cleanup → FTS rebuild
     - Batch sizes: FILE_BATCH=200, EMBED_BATCH=64

     3. Chunk Key = Physical Location (src/chunk/types.ts)
     - chunkKey = "file_path:startLine:endLine" — EXACTLY our Layer 2 primary key!
     - This validates our PRD Big-Rock-02 design completely.

     4. Tree-Sitter Chunking (src/chunk/treesitter.ts)
     - topLevelNodes per language (e.g., Rust: function_item, struct_item, enum_item, impl_item, trait_item...)
     - splitNodes: large items (>150 lines) get split into sub-items (methods within impl/class)
     - extractName(): language-specific logic for Go methods, Rust impls, Python decorators, etc.
     - extractSignature(): first line of the node = the signature

     5. Turso/libSQL Schema (src/db/schema.ts)
     - codebases table: id, root_path, name, indexed_at
     - chunks table: id, codebase_id, file_path, chunk_key (UNIQUE), language, kind, name, signature, snippet, start_line, end_line, file_hash, indexed_at, embedding (BLOB), embedding_model
     - indexed_files table: codebase_id, file_path, file_hash, chunk_count, indexed_at
     - Per-codebase FTS tables: fts_{codebase_id} with weighted fields (name=5.0, signature=3.0)
     - Vector search: vector_distance_cos(embedding, vector8(?)) — int8 quantized embeddings

     6. RRF Fusion (src/search/rank.ts)
     - score = 0.4/(60+rank_fts) + 0.6/(rank_vec+60) — standard RRF with k=60
     - Vector gets 60% weight, FTS gets 40%
     - Merges by chunkKey, sorts by combined score

     7. Query Preprocessing (src/search/query.ts)
     - Stopword removal (English + agent-specific filler like "help", "please", "file", "code")
     - Token regex: [a-z0-9]+(?:[-_.][a-z0-9]+)*
     - Max 12 terms, min 3 chars, max 30 chars

     8. MCP Server (src/mcp.ts)
     - 3 tools: codemogger_search, codemogger_index, codemogger_reindex
     - Dynamic descriptions: after indexing, search tool description updates with chunk/file counts
     - sendToolListChanged() after index operations — smart pattern for keeping LLM context fresh

     What NOT to Adopt from Codemogger

     - Embeddings (we're CPU-only, no vector search)
     - Bun/TypeScript runtime (we're Rust)
     - MCP as primary interface (we're HTTP-first)

     CACHEBRO - File Cache with Diff Tracking (INTERESTING FOR STALE DETECTION)

     What it is: Token-saving layer for AI agents. Caches file reads, returns diffs on subsequent reads instead of full content. 26-36% token savings.

     Patterns to Adopt

     1. Content-Addressed File Versioning
     - Schema: file_versions(path, hash, content, lines, created_at) — composite PK on (path, hash)
     - Every version of a file is stored. Hash = SHA-256 truncated to 16 chars.
     - session_reads(session_id, path, hash, read_at) — tracks what each session last saw

     2. FRESH/STALE Detection Pattern
     - Compare current file hash to last-seen hash in session
     - Same hash → FRESH (return one-line confirmation)
     - Different hash → STALE (compute and return unified diff)
     - This maps directly to our Screen 3 FRESH/STALE badge and Screen 7 staleness check

     3. Line-Based LCS Diff (src/differ.ts)
     - Longest Common Subsequence for line-level diffs
     - Returns unified diff format + exact changed line numbers
     - Could be useful for incremental re-analysis: only re-parse changed line ranges

     4. Session Isolation
     - Different sessions can be at different file versions
     - Useful if we ever need multi-user or multi-branch scenarios

     What NOT to Adopt from Cachebro

     - The caching layer itself (we don't cache file reads, we index)
     - The MCP proxy pattern (we're HTTP-first)
     - Token tracking/stats (interesting but out of scope)

     MEMELORD - Persistent Agent Memory (LOW PRIORITY BUT INTERESTING)

     What it is: Per-project persistent memory for coding agents. Memories survive across sessions, improve through reinforcement learning (weight adjustment based on agent feedback).

     Patterns Worth Noting

     1. Turso Connection Pattern — Short-Lived Connections
     - Opens/closes DB connection per operation to avoid multi-process lock contention
     - PRAGMA busy_timeout = 5000 for concurrent access
     - Retry with exponential backoff (max 10 attempts) if DB locked
     - IMPORTANT: This is a real-world lesson about Turso embedded driver file locking

     2. Per-Project DB Pattern
     - Each project gets .memelord/memory.db — no shared state across projects
     - Exactly matches our .parseltongue/index.db per-codebase pattern

     3. Vector Search in libSQL
     - vector_distance_cos(embedding, ?) for similarity search
     - Float32 vectors stored as BLOB
     - Works well enough for small-scale (hundreds/thousands of memories)

     What NOT to Adopt from Memelord

     - Memory/reinforcement learning system (different product)
     - Embeddings/vector search (we're CPU-only)
     - Claude Code hooks integration (interesting but not our interface)

     Key Validation for PRD-v300.md

     1. Big-Rock-02 CONFIRMED: codemogger uses file_path:startLine:endLine as its unique chunk key. Our physical-location-first primary key is the right call.
     2. D7 (Turso/libSQL) CONFIRMED: All three repos use Turso embedded. FTS + vector in single file works. Per-codebase FTS tables with weighted fields is production-proven.
     3. Incremental indexing via hashing CONFIRMED: SHA-256 per file, compare to stored hash, skip unchanged. Simple, fast, correct.
     4. .gitignore approach CONFIRMED: Simplified parsing (directory names only, no glob patterns) is sufficient. Practical tradeoff.
     5. memelord warns: Turso embedded driver has file locking issues with long-lived connections. Use short-lived connections or handle SQLITE_BUSY with retries.
