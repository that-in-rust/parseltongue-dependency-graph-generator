## Parseltongue Should Ship A Rust-First Walk Companion, Not A Broad Code Intelligence Platform

### SCQA

**Situation.** Parseltongue's older incarnation attempted to cover too much surface area: discovery, workflows, broad graph intelligence, and infrastructure-heavy architecture. The result is hard to trust, hard to explain, and not strong enough to showcase confidently in an interview.

**Complication.** A good interview demo needs to feel both technically original and tightly judged. A broad multi-language graph platform, a rank runtime, and a global OSS dataset thesis all add ambition, but they dilute the one thing that can be made visibly excellent soon: landing in an unfamiliar Rust codebase and walking its structure quickly.

**Question.** What is the smallest Parseltongue that is still differentiated, memorable, and honest?

**Answer.** `v313` should be a **Rust-first Walk Companion**: a local tree-sitter-based desktop tool that indexes a Rust repository, shows the repo map, extracts Rust entities and statement-aware local context, supports forward and backward dependency walking, and exports compact public-interface subgraphs without storing raw source code.

## The Governing Thought

`v313` wins if a user can point Parseltongue at a Rust repository and, within one minute, answer:

- what are the public entry points?
- what calls this?
- what does this call?
- what nearby statements inside this file matter?
- what is the likely blast radius of a change?

It does **not** win by claiming:

- complete multi-language truth
- compiler-verified semantics
- rank-based intelligence
- full OSS graph infrastructure
- a generic graph platform

## v313 Should Focus On One User Job

The core user job is:

> "I just landed in this Rust codebase. Help me orient myself, find the right entry point, and understand structural consequence without reading the whole repo."

This applies to:

- a human interviewer reviewing the tool
- an LLM agent trying to ground itself
- a developer joining an unfamiliar project

## Product Shape

`v313` has three product surfaces:

1. **Tauri desktop app**
   - add workspace
   - trigger indexing
   - trigger reindexing
   - inspect status and freshness
   - search entities
   - inspect a small graph and local file context

2. **Walk Graph Runtime**
   - forward walk
   - backward walk
   - bounded blast radius
   - public-anchor lookup
   - compact subgraph export

3. **Statement-aware reading layer**
   - for Rust entities only
   - returns ordered statement spans or local slices within the entity
   - helps the user read the current place, not just traverse away from it

## Non-Negotiable Constraints

- **Tree-sitter only.** No `rustc`, no MIR, no compiler plugins, no type-checker integration.
- **No raw code persistence.** Store only derived graph structure, metadata, paths, line spans, and confidence/freshness signals.
- **Rust-first depth.** Only `.rs` files receive full graph treatment in `v313`.
- **Other files stay coarse.** Non-Rust files are preserved as file-level context only.
- **No rank runtime.** `v313` does not include PageRank, HITS, Katz, eigenvector, or a dedicated scoring runtime.
- **No all-OSS product pipeline.** That remains a possible future thesis, not part of the first product scope.

## Supported Object Model

### Workspace hierarchy

The persistent workspace model is:

- `workspace`
- `folder`
- `file`
- `entity`

### File categories

Every file in the workspace must belong to exactly one category:

- `rust-file`
- `known-language-file`
- `opaque-file`

Definitions:

- `rust-file`: `.rs` file with deep indexing enabled
- `known-language-file`: recognized non-Rust code file such as `.ts`, `.js`, `.py`, `.go`, `.java`, `.c`, `.cpp`, `.rb`
- `opaque-file`: any other file type

### Why this split exists

This allows Parseltongue to preserve whole-repo context without pretending all languages are equally supported. The repo map stays honest and useful, while only Rust receives deep structural reasoning.

## Rust Entity Model

For `rust-file` nodes, Parseltongue extracts one file-level list of entities. `v313` should keep the entity model intentionally small:

- function
- struct
- enum
- trait
- impl-header
- method
- type-alias
- const
- static
- module
- import
- macro
- test
- comment
- gap

### Flattening rule

Nested Rust constructs may be represented as file-level entities when needed for usability. In particular:

- methods inside `impl` blocks are exposed as file-level method entities
- the `impl` header is preserved as its own entity when useful for orientation

This is a pragmatic flattening rule, not a compiler-truth model.

## Same-File Shared Context Should Exist, But Only For Reading

`v313` should keep a same-file context layer because code understanding is not only about cross-file dependency walking. Users also need to know what is near the current entity inside the file.

That said, same-file context should be treated as a **reading aid**, not a fake dependency edge.

Recommended behavior:

- entities in the same file may be listed as neighbors
- order should follow source position
- this relationship should be labeled clearly as `same_file_context`
- it should not be merged into call truth or blast-radius truth

## Statement Awareness Is In Scope

`v313` should support statement-level local context for Rust entities.

This means:

- for a Rust function or method, Parseltongue can return an ordered list of statement spans or local slices
- this layer is on-demand and local to the selected entity
- it does not become a full global graph of all statements

The purpose is:

- help the user read the selected place well
- make the tool feel like a reading companion, not only a dependency walker

It is not meant to become:

- a control-flow engine
- a data-flow engine
- a semantic simulator

## The Walk Graph Runtime Is The Only Runtime Required In v313

`v313` requires a walk-optimized graph runtime, not a rank runtime.

The runtime must support:

- direct forward neighbors
- direct backward neighbors
- bounded forward BFS
- bounded backward BFS
- blast radius by hop limit
- public-anchor walk
- compact subgraph export

This is enough to power the first product without building a second storage system for rank algorithms.

## Why Rank Runtime Is Explicitly Out Of Scope

Rank runtime is not required to prove the product thesis.

`v313` does not need:

- PageRank
- HITS
- Katz
- eigenvector centrality
- seeded PPR
- cluster ranking
- recommendation logic

If some ordering is needed, use cheap heuristics only:

- search score
- direct vs transitive
- public vs private
- hop distance
- degree count
- blast radius size

Those are ordering rules, not a dedicated rank runtime.

## Edge Families In v313

Only edge families that directly help the user job should be included.

### Required edges

- `contains`
  - workspace -> folder
  - folder -> folder
  - folder -> file
  - file -> entity

- `calls`
  - entity -> entity for Rust where structural extraction is possible

- `same_file_context`
  - entity -> entity within the same Rust file, ordered by source position
  - used for local reading context only

- `public_anchor`
  - derived relation when a private/internal entity is mapped to a public-facing entry point

### Explicitly deferred edges

- sibling folder edges
- sibling file edges
- same-parent topology edges that do not affect understanding directly
- generalized cross-language call edges

## Publicness And Anchoring

One of the most useful features in `v313` is the ability to move from an internal helper to the nearest meaningful public-facing entry point.

This should be treated as a best-effort structural feature.

Parseltongue may use:

- Rust visibility markers like `pub`
- module/file context
- bounded reverse walk

Parseltongue should not claim:

- exact semantic API boundaries
- guaranteed public-interface truth in all Rust patterns

## Minimal API Surface

The HTTP/API surface for `v313` should be intentionally small.

### Required endpoints

1. `GET /server-health-check-status`
   - confirms the local service is running

2. `GET /codebase-statistics-overview-summary`
   - returns workspace summary such as file counts, entity counts, language mix, freshness

3. `GET /code-entities-search-fuzzy?q=...`
   - search entry point for symbol lookup

4. `GET /code-entity-detail-view/{key}`
   - returns metadata for one entity or file

5. `GET /graph-walk-query?entity=...&direction=forward|backward|both&hops=N`
   - core walk endpoint for callers, callees, and bounded neighborhood

6. `GET /blast-radius-impact-analysis?entity=...&hops=N`
   - consequence-focused walk result

7. `POST /public-interface-subgraph-export`
   - returns a compact graph packet suitable for UI or LLM use

8. `GET /entity-local-reading-context/{key}`
   - returns same-file neighbors and statement-aware local slices for the selected Rust entity

### Optional simplification

If engineering simplicity is more important than endpoint purity, `blast-radius` and `local-reading-context` may be folded into `graph-walk-query` response modes.

## Tauri App Scope

The Tauri app should stay small and trustworthy.

### Required capabilities

- add local workspace
- show indexing state
- reindex workspace
- show freshness timestamp
- search entities/files
- inspect entity detail
- inspect forward/backward walk results
- inspect same-file local context
- visualize a small subgraph

### Explicitly not required

- full IDE
- code editor
- multi-pane architecture studio
- generic graph explorer for arbitrary edge families
- model-training interface

## Data Persistence

Parseltongue should persist:

- workspace metadata
- folder/file/entity metadata
- edge lists
- line spans
- language/file category
- public/private flags when applicable
- freshness and confidence metadata

Parseltongue should not persist:

- raw source file contents
- large embedded code snippets

## Demo Narrative

The interview-grade demo for `v313` should follow one path:

1. Open Tauri app
2. Add a Rust repository
3. Index repository
4. Search for a symbol
5. Open entity detail
6. Show forward and backward walk
7. Show public anchor if the symbol is internal
8. Show local file context and statement-aware slices
9. Export a compact public-interface subgraph

This is the product's magic moment:

> "I can land in unfamiliar Rust code, find the right entry point, and understand likely consequences fast."

## What v313 Is Not

`v313` is not:

- a general code intelligence platform
- a rank-heavy graph analytics engine
- a compiler-truth Rust analyzer
- a full polyglot dependency engine
- a global OSS graph pipeline
- a source-code archive

These may inform future versions, but they are not part of the first credible product.

## Most Ambiguous Build Areas

The following areas remain ambiguous and should be handled carefully.

### 1. Call-edge accuracy

Tree-sitter-based call extraction is structurally useful but imperfect. This is the single biggest trust risk.

### 2. Public-anchor resolution

Mapping internal helpers to the "right" public-facing entry point is useful but can become misleading if overclaimed.

### 3. Statement boundary selection

Statement-aware local context is in scope, but the exact return shape needs care. The product should decide whether to return:

- AST-derived statements
- source spans
- human-friendly labeled slices

### 4. Flattened entity policy

Rust `impl` blocks and methods are natural candidates for flattening, but the precise representation should favor user comprehension over theoretical purity.

### 5. Same-file context semantics

The feature is valuable, but it must remain clearly labeled as co-location/context, not dependency truth.

## Acceptance Criteria

`v313` is successful when all of the following are true:

- user can add and index a local Rust repository from the Tauri app
- user can search for a symbol
- user can inspect entity metadata and file span
- user can walk forward and backward from the selected entity
- user can inspect bounded blast radius
- user can see same-file local context and statement-aware slices for Rust entities
- user can export a compact public-interface subgraph
- the system stores no raw source code
- the system makes no compiler-truth claims

## Future Extensions, Explicitly Deferred

The following are intentionally deferred beyond `v313`:

- full multi-language deep indexing
- cross-language bridge edges
- rank runtime
- cluster/community algorithms
- all-OSS dataset pipeline
- diff and simulation across snapshots
- semantic or compiler-backed truth layers

## Final Recommendation

`v313` should be built and presented as:

> **Parseltongue Rust Walk**

That name is honest about scope and strong on product shape:

- `Parseltongue` preserves the brand
- `Rust` states the deep-support boundary
- `Walk` highlights the differentiated capability

The internal technical label may remain:

> **Walk Graph Runtime**

But the product itself should be sold as a Rust-first code-reading companion that makes dependency walking and local structural reading fast and trustworthy enough to matter.
