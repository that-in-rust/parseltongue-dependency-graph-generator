# Parseltongue Root-Span Call Graph Architecture

**Version:** Arch-v202607210

**Status:** Proposed architecture for a complete rewrite

**Decision:** CodeMogger-first, Rust-native, Turso-backed

**Product contract:** [prd-v20260710.md](prd-v20260710.md)

**Prepared:** 2026-07-10

---

## 1. Executive Decision

Parseltongue should be rebuilt as a small, trustworthy code-capture daemon whose
primary architectural inspiration is CodeMogger.

CodeMogger has the right basic shape:

1. Keep language support in one explicit manifest.
2. Detect a file's language.
3. Parse the file with Tree-sitter.
4. inspect direct children of the syntax root.
5. Turn those children into stable, persisted records.
6. Store the current index in embedded Turso.
7. Serve fast local queries from that index.

Parseltongue should preserve that simplicity, but it cannot copy CodeMogger
literally. CodeMogger is primarily a retrieval chunker. Parseltongue is now a
current-state architecture and call-graph product. It therefore needs stronger
semantics around source accounting, identity, call evidence, graph resolution,
change reconciliation, and publication.

The selected architecture is:

> **A CodeMogger-style Tree-sitter capture pipeline, rewritten idiomatically in
> Rust, with Turso as the canonical current-state store, CocoIndex-inspired
> source positions and desired-state reconciliation, and Parseltongue-specific
> Root-Span Graph semantics.**

The public HTTP query surface remains deliberately small. It exposes exactly
three read operations:

1. **GET /code-entities-search-fuzzy?q=...**
2. **GET /forward-callees-query-graph?entity=...**
3. **GET /reverse-callers-query-graph?entity=...**

The required local CLI performs indexing, byte verification, file-ledger
inspection, and capture reporting. It does not add an HTTP route. The daemon and
storage system exist to make the graph queries and accounting report
trustworthy. There is no public generic graph query endpoint, no architecture
history, no diff API, no embeddings API, and no transitive graph API in this
scope.

### 1.1 The central product thesis

The useful product is not "a graph database for code." It is:

> **A dependable local instrument that continuously converts a repository into
> an evidence-bearing, one-hop callable graph that humans and coding agents can
> inspect without rereading the whole repository.**

The architecture is optimized for trust:

- Every discovered file receives an explicit capture status.
- Every byte of every supported text file is classified exactly once as
  INTERFACE_CODE, COMMENT, or UNKNOWN_CODE.
- Calculated and independently read persisted manifests must match before
  publication.
- Every entity points back to exact source coordinates.
- Every resolved call edge is backed by one or more syntax observations.
- Ambiguity remains ambiguity instead of being promoted into a false fact.
- A filesystem change publishes atomically as a new current revision.
- An incremental update must produce the same state as a clean rebuild.
- Empty graph results are distinguishable from indexing or storage failures.

### 1.2 Why CodeMogger wins over the alternatives

CodeMogger is the best primary inspiration because its abstraction starts at the
right level: **file to language pack to syntax root to persisted record**. That
matches the reduced product more closely than a general graph framework, a
vector-indexing pipeline, a compiler front end, or an external graph database.

Petgraph is not required for the first version. The product asks only for direct
forward and reverse adjacency, which indexed relational tables can answer
accurately and cheaply. Adding an in-memory graph would create a second state
representation, a cache-invalidation problem, and a startup hydration cost
without enabling a required public behavior.

Neo4j is also unnecessary. It adds deployment and operational surface while the
required graph work is two indexed one-hop lookups. Cozo's temporal and Datalog
model is no longer aligned with the reduced current-state product.

Turso is the selected store because CodeMogger demonstrates the local
code-indexing precedent, the data is naturally relational, transactions give
atomic publication, and forward and reverse call queries map directly to
ordinary indexes.

## 2. Scope Contract

This architecture is subordinate to the narrowed PRD. It must not quietly
reintroduce the former broad product.

### 2.1 Required behavior

The system shall:

- Capture one configured local repository.
- Perform a complete initial scan.
- Continue monitoring changes through a local daemon.
- Recognize the initial language families defined by the language manifest.
- Parse supported source with Tree-sitter language packs.
- Divide each supported readable file into top-level root spans and an exact
  three-class source ledger.
- Extract addressable functions, methods, constructors, and container symbols.
- Detect call observations and resolve them conservatively.
- Persist one current repository state in embedded Turso.
- Publish changes as monotonic capture revisions.
- Provide a local indexing, deep-verification, file-inspection, and
  capture-report CLI.
- Report calculated and persisted byte totals, class totals, hashes, and
  derived-record counts after indexing.
- Return deterministic fuzzy entity search.
- Return direct forward callees.
- Return direct reverse callers.
- Include source evidence and uncertainty in results.

### 2.2 Explicit non-goals

The rewrite shall not include:

- Historical snapshots.
- Architecture diffs.
- Pull-request comparison.
- Temporal graph queries.
- Transitive callers or callees.
- Blast-radius scoring.
- Centrality, distance, clustering, or community detection.
- Vector embeddings.
- Semantic retrieval chunks.
- LLM prompt construction.
- Code generation or modification.
- Generic SQL, Datalog, Cypher, or graph-query access.
- A public file-content endpoint.
- A public daemon-status endpoint.
- Multiple repositories in one daemon.
- Tree-sitter incremental edit reuse in the first release.
- A second in-memory graph as a source of truth.

Operational status and byte-accounting evidence are available through process
exit codes, structured logs, and the required local CLI. The CLI does not create
a fourth HTTP API.

### 2.3 Behavioral invariants

| ID | Invariant |
|---|---|
| ARC-INV-001 | A successful API response is derived from one committed capture revision. |
| ARC-INV-002 | A known entity with no direct calls returns HTTP 200 with an empty collection. |
| ARC-INV-003 | A storage or capture failure never masquerades as an empty graph. |
| ARC-INV-004 | Every resolved call edge has at least one persisted call-site observation. |
| ARC-INV-005 | No call observation is upgraded from ambiguous to resolved without repository evidence. |
| ARC-INV-006 | Every supported readable text file has a complete, gap-free byte ledger over [0, byte_length). |
| ARC-INV-007 | Line and column coordinates are metadata, never durable identity. |
| ARC-INV-008 | Replaying the same repository state produces the same observable graph and search results. |
| ARC-INV-009 | Incremental reconciliation and a clean rebuild are observably equivalent. |
| ARC-INV-010 | The HTTP router contains exactly the three PRD routes. |
| ARC-INV-011 | Every byte is classified exactly once as INTERFACE_CODE, COMMENT, or UNKNOWN_CODE. |
| ARC-INV-012 | Interface-code bytes plus comment bytes plus unknown-code bytes equal captured and persisted source bytes. |
| ARC-INV-013 | Calculated and independently read persisted manifests match before a revision is committed. |
| ARC-INV-014 | Confirmed comment bytes are never also counted as interface-code bytes. |

## 3. Evidence Synthesis

This design combines three bodies of local evidence. CodeMogger is the primary
blueprint. CocoIndex contributes selected incremental-data ideas. Parseltongue's
existing code and research corpus provide the failure cases and stronger domain
semantics.

### 3.1 What is adopted from CodeMogger

The local CodeMogger repository contains a compact language configuration model
with language name, extensions, grammar location, top-level node kinds, and
split-node kinds:

- [languages.ts](../../git-ref-repo/ignore-this-folder-repos/glommer__codemogger/src/chunk/languages.ts)
- [treesitter.ts](../../git-ref-repo/ignore-this-folder-repos/glommer__codemogger/src/chunk/treesitter.ts)
- [store.ts](../../git-ref-repo/ignore-this-folder-repos/glommer__codemogger/src/db/store.ts)
- [schema.ts](../../git-ref-repo/ignore-this-folder-repos/glommer__codemogger/src/db/schema.ts)

The most important CodeMogger behavior is that it begins extraction from direct
children of the syntax root. A top-level function therefore owns local
functions nested within it instead of recursively turning every nested syntax
node into a peer. That is the correct starting intuition for Parseltongue's
Root-Span model.

CodeMogger also demonstrates:

- One central language registry.
- Parser and grammar reuse.
- Language-specific top-level syntax mappings.
- A local Turso-backed index.
- File replacement as a desired-state operation.
- A small pipeline that can be understood end to end.

### 3.2 What is deliberately changed from CodeMogger

CodeMogger's implementation also exposes boundaries that Parseltongue must
strengthen:

| CodeMogger behavior | Parseltongue decision |
|---|---|
| Chunk identity includes path and line range | Use a store-assigned opaque entity ID; spans are mutable metadata |
| Large declarations can be split into retrieval chunks | Never let token or line limits redefine architecture entities |
| A large container can disappear when split into members | Preserve the container RootSpan and separately expose addressable members |
| File chunks are deleted and recreated | Reconcile a desired file state while preserving high-confidence entity identities |
| Records primarily support retrieval | Persist entities, observations, candidates, resolved edges, source segments, and diagnostics |
| No complete source accounting | Store a gap-free source ledger |
| No caller/callee graph | Resolve evidence-bearing one-hop call edges |
| No explicit ambiguity model | Persist resolved, ambiguous, external, and unresolved states |

The rewrite is therefore best described as **CodeMogger plus graph
trustworthiness**, not as a port.

### 3.3 What is adopted from CocoIndex

The local CocoIndex code-indexing example contributes two useful ideas:

- Rich positions should preserve byte offset, character offset, line, and
  column instead of collapsing location into line numbers.
- Indexing should be modeled as desired dataflow state that is reconciled
  incrementally, rather than as a loose sequence of mutation callbacks.

Evidence:

- [indexer.py](../../git-ref-repo/ignore-this-folder-repos/cocoindex-io__cocoindex-code/src/cocoindex_code/indexer.py)
- [chunking.py](../../git-ref-repo/ignore-this-folder-repos/cocoindex-io__cocoindex-code/src/cocoindex_code/chunking.py)
- [shared.py](../../git-ref-repo/ignore-this-folder-repos/cocoindex-io__cocoindex-code/src/cocoindex_code/shared.py)

CocoIndex's overlapping, byte-budgeted retrieval chunks are not used as
architecture nodes. Retrieval chunks answer "what text fits in a context
window?" Root spans answer "what top-level construct owns this source?" Those
are different products and must remain different models.

### 3.4 What is retained from Parseltongue research

The Tree-sitter corpus in [research003](../research003/) provides the detailed
engineering constraints:

- Central, versioned language registries.
- Exclusive mutable parser ownership.
- Query-family separation.
- Typed capture names.
- Exact source provenance.
- Scope-aware call ownership.
- Cache keys that include source, grammar, queries, and extractor versions.
- Full-rebuild parity testing.
- Golden multilingual fixtures.
- Query compilation tests.
- Parse-quality reporting using ERROR and MISSING nodes.
- Deletion and orphan-cleanup tests.
- Resource bounds and failure diagnostics.

Primary references:

- [tree-sitter-patterns-1.md](../research003/tree-sitter-patterns-1.md)
- [tree-sitter-patterns-2.md](../research003/tree-sitter-patterns-2.md)
- [tree-sitter-patterns-3.md](../research003/tree-sitter-patterns-3.md)
- [tree-sitter-patterns-4.md](../research003/tree-sitter-patterns-4.md)
- [tree-sitter-patterns-5.md](../research003/tree-sitter-patterns-5.md)

The corpus is broad and useful, but its own completion audit notes that it is a
curated evidence base rather than a verified exhaustive reading of every
reference repository. Architecture claims in this document rely on the cited
local files and should not be presented as universal industry facts.

### 3.5 Problems in the current Parseltongue implementation

The existing code is useful evidence, but it is not the target architecture:

- [query_extractor.rs](../../crates/parseltongue-core/src/query_extractor.rs)
  compiles language queries during parsing, deduplicates entities by mutable
  name and line range, and leaves call targets incompletely resolved.
- [isgl1_v2.rs](../../crates/parseltongue-core/src/isgl1_v2.rs) derives a
  synthetic birth timestamp and uses content and nearby lines as identity
  signals. Those are reconciliation evidence, not durable primary keys.
- [incremental_reindex_core_logic.rs](../../crates/pt08-http-code-query-server/src/incremental_reindex_core_logic.rs)
  is file-oriented but does not model deletion, incoming-edge invalidation, and
  whole-revision publication strongly enough.
- [file_watcher_integration_service.rs](../../crates/pt08-http-code-query-server/src/file_watcher_integration_service.rs)
  can spawn independent event work, which makes ordering and publication harder
  to reason about.
- [code_entities_fuzzy_search_handler.rs](../../crates/pt08-http-code-query-server/src/http_endpoint_handler_modules/code_entities_fuzzy_search_handler.rs)
  implements lowercase substring matching and can collapse backend failures
  into empty-looking behavior.
- [forward_callees_query_graph_handler.rs](../../crates/pt08-http-code-query-server/src/http_endpoint_handler_modules/forward_callees_query_graph_handler.rs)
  treats "known entity with no callees" like absence.
- [route_definition_builder_module.rs](../../crates/pt08-http-code-query-server/src/route_definition_builder_module.rs)
  registers a much larger HTTP surface than the narrowed product.

The rewrite should preserve lessons and fixtures where useful, but should not
wrap the old temporal model in new names.

## 4. Architecture Overview

### 4.1 System context

~~~mermaid
flowchart TB
    User["Human or coding agent"]
    API["Three-route HTTP API"]
    Query["Current graph query service"]
    Store["Embedded Turso current-state database"]
    Daemon["Capture daemon and single writer"]
    Parser["Tree-sitter language packs"]
    Repo["Local repository"]

    User --> API
    API --> Query
    Query --> Store
    Repo --> Daemon
    Daemon --> Parser
    Parser --> Daemon
    Daemon --> Store
~~~

The database is the canonical read model and source of truth for the current
capture. Tree-sitter trees, parser workers, and temporary desired states are
ephemeral implementation details. No public response depends on an uncommitted
in-memory graph.

### 4.2 Capture pipeline

~~~mermaid
flowchart TB
    Discover["Discover and classify files"]
    Hash["Hash and skip unchanged content"]
    Parse["Parse with an exclusive parser worker"]
    Roots["Extract root spans and entities"]
    Ledger["Build three-class byte ledger"]
    Observe["Extract call observations"]
    Desired["Construct desired file state"]
    Match["Reconcile durable identities"]
    Resolve["Resolve affected call observations"]
    Validate["Compare calculated and persisted manifests"]
    Commit["Commit one atomic revision"]

    Discover --> Hash
    Hash --> Parse
    Parse --> Roots
    Roots --> Ledger
    Roots --> Observe
    Ledger --> Desired
    Observe --> Desired
    Desired --> Match
    Match --> Resolve
    Resolve --> Validate
    Validate --> Commit
~~~

### 4.3 Runtime processes

The first implementation uses one operating-system process:

- One Tokio runtime.
- One capture coordinator.
- One serialized database writer.
- A bounded set of parser workers.
- A filesystem watcher feeding a coalescing queue.
- A read-only query service.
- One Axum HTTP server exposing exactly three routes.

This can later be split if evidence requires it. A multiprocess architecture is
not justified for a local single-repository product.

### 4.4 Source of truth

| Concern | Authoritative representation |
|---|---|
| Repository contents | Filesystem |
| Current parsed model | Committed Turso revision |
| In-progress update | Ephemeral desired state owned by capture coordinator |
| Public entity identity | Opaque EntityId persisted in Turso |
| Source location | SourceSpan tied to FileId and content hash |
| Graph fact | CallEdge backed by CallObservation records |
| Capture readiness | capture_meta row plus daemon state |
| Language capability | Versioned LanguagePackManifest |

## 5. Domain Model

The core domain is intentionally smaller than the existing temporal entity
model. It represents current source, current entities, and current one-hop call
evidence.

### 5.1 Boundary newtypes

Rust code should use explicit newtypes at every identity and revision boundary:

~~~rust
pub struct RepositoryId(Uuid);
pub struct CaptureRevision(u64);
pub struct FileId(Uuid);
pub struct RootSpanId(Uuid);
pub struct EntityId(Uuid);
pub struct SourceSegmentId(Uuid);
pub struct CallObservationId(Uuid);
pub struct CallEdgeId(Uuid);

pub struct ContentHash([u8; 32]);
pub struct ParserFingerprint([u8; 32]);
pub struct QueryBundleHash([u8; 32]);
~~~

Entity IDs should be opaque UUIDv7 values assigned by the store when a new
logical entity is first accepted. They must not encode a line, path, language,
name, signature, content hash, or synthetic timestamp.

### 5.2 Position and span

~~~rust
pub struct TextPosition {
    pub byte_offset: u64,
    pub char_offset: u64,
    pub line: u32,
    pub column: u32,
}

pub struct SourceSpan {
    pub file_id: FileId,
    pub source_hash: ContentHash,
    pub start: TextPosition,
    pub end: TextPosition,
}
~~~

Rules:

- Spans are half-open: [start, end).
- Byte offsets are authoritative for slicing source.
- Line and column are zero-based internally.
- API DTOs may expose one-based display lines, but must label them clearly.
- Character offsets count Unicode scalar values, not bytes.
- Columns use one documented convention and receive UTF-8 golden tests.
- A span is meaningful only with FileId and source hash.

### 5.3 File record

A FileRecord exists for every in-scope, nonignored regular file discovered under
the repository root, including files that cannot be parsed. Ignore decisions
are recorded in the discovery summary and policy fingerprint rather than
materialized as current file rows.

Required fields:

- FileId.
- Normalized repository-relative path.
- Filesystem identity hints when available.
- ContentHash.
- Byte length and line count.
- Language detection outcome.
- Capture status.
- Parser fingerprint.
- Parse-quality summary.
- Source bytes for supported text files.
- Last committed capture revision.

Capture status is one of:

- parsed
- parsed_with_errors
- unsupported_language
- binary
- too_large
- unreadable

Every path presented to the discovery stage must end in an explicit decision.
Deletion is a reconciliation operation that removes the file's current-state
row; it is not a status retained in the current-state table.

### 5.4 RootSpan

A RootSpan is the non-overlapping ownership envelope for a direct construct
under the file's syntax root.

Examples:

- A Rust free function.
- A Rust impl block.
- A Java class.
- A Java top-level declaration.
- A Python module-level function.
- A JavaScript module-level function or class.
- A Go function or type declaration.
- A C or C++ function definition.
- A Ruby top-level class, module, or method definition.

Required fields:

- RootSpanId.
- FileId.
- Language-neutral root kind.
- Grammar-specific node kind.
- Optional display name.
- Exact SourceSpan.
- Content hash.
- Extraction confidence.
- Parse-quality flags.

Root spans for one file must not overlap. If a grammar inserts a transparent
wrapper such as a declaration list, the language pack may descend through that
wrapper exactly once to identify semantic roots.

### 5.5 AddressableEntity

An AddressableEntity is a symbol that may be returned by fuzzy search or used as
the source or target of a call edge.

Initial entity kinds:

- function
- method
- constructor
- class
- struct
- enum
- trait
- interface
- module
- namespace
- impl
- unknown_declaration

Required fields:

- EntityId.
- FileId and RootSpanId.
- Optional owner EntityId.
- Normalized kind.
- Grammar-specific kind.
- Name and qualified name.
- Display signature.
- Visibility when reliably known.
- Exact SourceSpan.
- Signature span when available.
- Descriptor hash.
- Signature hash.
- Body hash.
- Search text.
- Parse-quality and extraction-confidence fields.

Container entities and callable entities can coexist. A Java class RootSpan can
own method entities. A Rust impl RootSpan can own method entities. This preserves
one top-level accounting envelope without throwing away the call precision
needed by forward and reverse queries.

Nested local functions and closures do not become peer addressable entities in
the first release. Their source remains owned by the nearest addressable
callable. A call found inside such a nested construct carries a lexical-context
marker so the API does not imply more runtime certainty than the syntax proves.

### 5.6 SourceSegment

SourceSegment is the exact accounting ledger. Segments are atomic,
non-overlapping intervals that partition a supported text file.

There are exactly three primary accounting classes:

~~~rust
pub enum SourceByteClass {
    InterfaceCode,
    Comment,
    UnknownCode,
}
~~~

- **INTERFACE_CODE** means bytes owned by an accepted file-level RootSpan after
  confirmed comment bytes and conservatively identified error bytes are removed.
- **COMMENT** means bytes conclusively identified as comment syntax by the
  language pack.
- **UNKNOWN_CODE** means every remaining byte. This includes unclaimed syntax,
  malformed or incomplete regions, unsupported constructs, file-level
  whitespace outside a RootSpan, and any byte for which ownership is not
  defensible.

Each segment may point to:

- Its RootSpan owner.
- Its most specific AddressableEntity owner.
- The grammar node kind that produced the classification.
- A confidence and diagnostic code.
- A hash of the exact source slice.
- An optional unknown-reason code.

Classification uses one fixed precedence:

1. A confirmed comment range is COMMENT even when it lies inside a RootSpan.
2. Remaining defensible bytes inside an accepted RootSpan are INTERFACE_CODE.
3. Every byte still unclaimed is UNKNOWN_CODE.

Methods, constructors, and other member entities are semantic overlays within a
RootSpan. They never add accounting bytes and therefore cannot double-count the
container. Their identity and spans remain available for search and call edges.

For a nonempty file with N bytes, sorted segments must satisfy:

- The first segment starts at byte 0.
- Every segment starts where the previous one ends.
- No segment is empty.
- The final segment ends at byte N.
- Every segment has exactly one SourceByteClass.
- The segment hash equals the hash of source_bytes[start_byte..end_byte].

An empty file has zero segments and zero bytes in all three classes. This is a
valid exact ledger, not a missing-capture error.

The exact accounting equation is:

~~~text
interface_code_bytes + comment_bytes + unknown_code_bytes
    == calculated_source_bytes
    == persisted_source_bytes
    == N
~~~

Entities may geometrically contain other entity spans. SourceSegment rows do not
overlap because byte class is independent from semantic entity overlays.
Comments remain COMMENT while retaining optional RootSpan and entity ownership
metadata.

Parser errors, invalid encoding evidence, unsupported syntax, ambiguous
ownership, and unclaimed gaps are diagnostic reasons, not additional primary
byte classes. This keeps the accounting equation stable while allowing edge-case
understanding to improve over time.

Tree-sitter MISSING nodes are often zero-width and therefore cannot be
SourceSegments. They are stored as ParseMarker records at an exact byte offset.
Tree-sitter ERROR ranges contain bytes and are classified conservatively as
UNKNOWN_CODE unless a more reliable confirmed comment range takes precedence.

Ledger construction is a deterministic interval-sweep:

1. Begin with [0, N) provisionally classified as UNKNOWN_CODE.
2. Overlay accepted non-overlapping RootSpan ranges as INTERFACE_CODE.
3. Overlay Tree-sitter ERROR and other indefensible ranges back to UNKNOWN_CODE.
4. Overlay confirmed comment ranges last as COMMENT.
5. Add every interval boundary, sort and deduplicate the boundaries, and emit
   adjacent half-open segments.
6. Attach semantic owners and diagnostic reasons without changing the primary
   byte class.
7. Merge adjacent segments only when class, ownership, diagnostics, and hashing
   policy permit it.
8. Hash each final source slice and calculate file totals.

This is run-length encoding over exact source intervals, not one database row
per byte. It gives byte-for-byte proof without pathological row counts.

### 5.7 CallObservation

A CallObservation records what the parser saw before deciding what the callee
means.

Required fields:

- CallObservationId.
- Source FileId.
- Source EntityId.
- Exact call-site SourceSpan.
- Raw callee text.
- Optional receiver text.
- Syntax form.
- Lexical-context kind.
- Import and scope hints.
- Resolution key.
- Resolution state.
- Resolver version.
- Diagnostic detail.

Resolution states are:

- resolved
- ambiguous
- external
- unresolved

The observation is preserved in every state. This is essential for explaining
why an edge exists or why an edge could not be created.

### 5.8 CallCandidate, CallEdge, and CallSite

A CallCandidate connects an ambiguous observation to a possible internal target
with a rank and reason. Candidates are evidence, not graph facts.

A CallEdge connects one internal source entity to one internal target entity.
There is at most one edge for a source-target-resolution tuple.

A CallSite connects a CallEdge to each supporting CallObservation. Multiple call
sites between the same pair therefore produce one graph edge with multiple
pieces of source evidence.

Forward and reverse graphs are views over the same CallEdge table:

- Forward query filters by source EntityId.
- Reverse query filters by target EntityId.

This symmetry is a correctness invariant and a simple property test.

## 6. Root-Span Semantics

### 6.1 The one-layer rule

The file is the accounting root. Parseltongue first examines direct semantic
children of that root. It does not recursively promote every nested declaration
into a peer architecture node.

For example:

~~~text
file
  function abc
    local function helper_one
    local function helper_two
    closure
~~~

The Root-Span Graph contains one root span for function abc. The local
functions and closure remain part of abc's owned implementation. Calls inside
them are observations owned by abc with a nested lexical-context marker.

This rule controls architecture noise and preserves a comprehensible top-level
map.

### 6.2 The member exception

Object-oriented and trait-oriented languages require callable members to remain
addressable:

~~~text
file
  class AccountService
    constructor
    method create_account
    method close_account
~~~

The class is one RootSpan and one container entity. Its constructor and methods
are child AddressableEntities. They are not separate root spans.

This is not unbounded recursive decomposition. Extraction stops at direct
callable members. Local functions and closures inside a method remain owned by
the method.

Without this exception, a forward call from one method or a reverse call to one
method would be forced onto the whole class, which would make the three public
queries materially less useful.

### 6.3 Architecture entities are not retrieval chunks

Entity boundaries are defined by syntax and ownership, never by:

- A token budget.
- A maximum line count.
- An embedding window.
- A text-overlap setting.
- A UI pagination limit.

A 900-line function is still one architecture entity. The parser may protect
itself with file-size and time limits, but it may not split the function into
fake architecture peers. A later retrieval product can create separate
overlapping chunks that reference EntityId without changing the graph.

### 6.4 Imperfect parse behavior

Tree-sitter can return a tree that includes ERROR and MISSING nodes. The capture
pipeline should salvage high-confidence roots and entities while reporting
quality.

Rules:

- A parser error is not a reason to silently keep stale entities from the old
  file.
- High-confidence unaffected roots may still be published.
- Error, dangling, incomplete, and otherwise unclaimed byte ranges become
  UNKNOWN_CODE segments with diagnostic reasons.
- Confirmed comments remain COMMENT even when neighboring syntax is malformed.
- Zero-width MISSING nodes become ParseMarker diagnostics and do not alter byte
  totals.
- Entities intersecting severe errors receive reduced confidence.
- A completely unparseable supported file remains represented as a FileRecord
  whose readable bytes are partitioned into COMMENT and UNKNOWN_CODE, with no
  fabricated entities.

## 7. Language-Pack Architecture

### 7.1 One product manifest

CodeMogger's central language configuration should become a typed Rust manifest:

~~~rust
pub struct LanguagePackManifest {
    pub language: LanguageId,
    pub extensions: &'static [&'static str],
    pub filenames: &'static [&'static str],
    pub grammar_version: &'static str,
    pub query_bundle_hash: QueryBundleHash,
    pub extractor_version: &'static str,
    pub root_node_kinds: &'static [&'static str],
    pub transparent_root_wrappers: &'static [&'static str],
    pub capabilities: LanguageCapabilities,
}
~~~

The manifest is both implementation configuration and the product's auditable
language-support contract.

Initial language packs should cover the requested families:

- Rust.
- JavaScript.
- TypeScript.
- TSX.
- Java.
- Kotlin.
- C.
- C++.
- Go.
- Python.
- Ruby, including Rails source conventions.

Support is not advertised merely because a grammar crate compiles. A pack is
available only when its query compilation, capture contracts, ownership
fixtures, call fixtures, and source-ledger fixtures pass.

### 7.2 Query families

Each language pack owns separate query files:

~~~text
languages/
  rust/
    roots.scm
    entities.scm
    comments.scm
    calls.scm
    scopes.scm
    imports.scm
  typescript/
    roots.scm
    entities.scm
    comments.scm
    calls.scm
    scopes.scm
    imports.scm
~~~

The files have different responsibilities:

| Query family | Responsibility |
|---|---|
| roots.scm | Coarse direct file-root candidates |
| entities.scm | Names, signatures, members, and container relationships |
| comments.scm | Confirmed language comment ranges used by the byte ledger |
| calls.scm | Call-expression candidates and syntax forms |
| scopes.scm | Lexical ownership and local binding hints |
| imports.scm | Import, alias, package, module, and use hints |

Query captures should use a typed taxonomy such as:

- root.declaration
- entity.name
- entity.signature
- entity.body
- member.callable
- comment.confirmed
- call.expression
- call.target
- call.receiver
- scope.local
- import.path
- import.alias

String capture names are converted immediately into a Rust enum. Unknown capture
names fail the language-pack contract test.

### 7.3 Query plus traversal

Queries identify coarse candidates. Language-specific Rust refiners use
field-name access and bounded cursor traversal for details.

This hybrid avoids two common failures:

- A giant query that tries to encode every grammar exception.
- Generic recursive traversal that guesses meaning from node-kind strings.

The common pipeline depends on a LanguagePack trait. Language-specific code may
diverge behind that trait where grammars genuinely differ.

### 7.4 Parser workers

Tree-sitter Parser is mutable and should have exclusive ownership while parsing.

The runtime uses a bounded parser-worker pool:

- A worker owns one Parser and caches loaded Language objects.
- A parser is never shared concurrently.
- Work is bounded by file count and memory limits.
- Query objects are compiled once at startup for each enabled pack.
- Compiled queries are immutable and shared through Arc where bindings permit.
- A failed query compilation disables that pack and emits a clear startup
  diagnostic.

The parser cache fingerprint includes:

- Source content hash.
- Grammar name and version.
- Query bundle hash.
- Extractor version.
- Position-model version.

Changing any component invalidates prior derived records.

### 7.5 Language-specific correctness

Normalization should unify only concepts that are truly shared. The common
model may say method, function, import, call, or container, while preserving the
original grammar kind and language-specific details.

Examples of required divergence:

- Rust associated functions, trait methods, macros, and impl ownership.
- Java overloads, constructors, packages, and static calls.
- Kotlin companion objects and extension functions.
- C and C++ declarations, definitions, namespaces, operators, and macros.
- JavaScript and TypeScript member access, optional chaining, imports, and
  dynamic calls.
- Python decorators, async functions, class methods, and nested functions.
- Ruby modules, singleton methods, implicit receiver calls, and Rails DSLs.

Unsupported dynamic or macro-generated meaning remains unresolved or external.
The graph should not pretend to be a compiler.

## 8. Call Extraction and Resolution

### 8.1 Two-phase model

Call processing is divided into:

1. **Observation:** What call-like syntax exists, where is it, and who owns its
   source bytes?
2. **Resolution:** Which current internal entity, if any, does that observation
   identify?

This separation allows the repository's symbol set to change without reparsing
every source file.

### 8.2 Observation ownership

The nearest AddressableEntity owns a call observation.

- A call in a free function belongs to that function.
- A call in a method belongs to that method.
- A call in a constructor belongs to that constructor.
- A call in a local function nested inside a free function belongs to the outer
  function and is marked nested_owned.
- A call in a closure belongs to the outer callable and is marked closure_owned.
- A call in a class initializer belongs to the relevant constructor or
  container according to the language pack.

The resulting graph is a **lexical call-reference graph**, not a proof of runtime
execution. API responses expose lexical context to preserve that distinction.

### 8.3 Conservative resolution sequence

The resolver attempts, in order:

1. Exact local binding or direct member identity proven by the language pack.
2. Exact qualified name.
3. Exact import or alias expansion.
4. Exact symbol in the same container, module, namespace, or package.
5. Unique repository-wide normalized candidate.
6. Ranked internal candidates without selecting a winner.
7. External classification when syntax or imports prove the target is outside
   the repository.
8. Unresolved classification.

A unique textual name is not always a unique semantic target. Overloads,
inheritance, traits, dynamic dispatch, macros, and implicit receivers require
language-specific caution.

### 8.4 Edge creation rule

A CallEdge is created only when:

- Both endpoints are current internal AddressableEntities.
- The observation has one accepted target.
- The resolver records the evidence and algorithm version.
- The source span still matches the current source hash.

Ambiguous observations produce CallCandidate records but no CallEdge. External
and unresolved observations remain visible in forward-query evidence but do not
create internal graph edges.

### 8.5 Resolution invalidation

Parsing only changed files is insufficient when a changed file adds, removes,
moves, or renames a callable. Existing observations in other files may resolve
differently.

The first implementation uses a correctness-first policy:

- If a changed batch modifies only callable bodies while preserving the symbol
  surface, resolve the changed observations.
- If names, qualified names, ownership, imports, signatures used for
  disambiguation, or files change, re-resolve all current observations before
  committing.
- Compare the result to clean-rebuild parity fixtures.

This is intentionally simpler than a premature resolution-dependency index.
Later, persisted lookup keys may restrict re-resolution, but only after parity
tests prove identical output.

## 9. Identity and Reconciliation

### 9.1 Identity principles

Identity answers "is this the same logical entity after a file edit?" No single
source attribute can answer that perfectly.

The system therefore separates:

- **Identity:** Opaque EntityId assigned once and persisted.
- **Descriptor:** Name, kind, owner, and qualified path used for matching.
- **Fingerprint:** Signature, structure, and body hashes used as evidence.
- **Location:** Mutable SourceSpan.
- **Revision:** The committed capture in which the current record is visible.

Content hashes and line spans are evidence. They are not primary keys.

### 9.2 Entity matching ladder

For each desired entity in a changed file, reconciliation attempts:

1. Exact normalized descriptor under the same preserved owner.
2. Exact signature fingerprint under the same owner.
3. Unique body or structure fingerprint within the file.
4. Unique moved fingerprint across a paired file rename.
5. Near position as a weak tie-breaker only.
6. No match when evidence remains ambiguous.

If two old entities are equally plausible, the reconciler must allocate a new
EntityId rather than force continuity. False continuity is more damaging than a
new identity because it misattributes graph evidence.

### 9.3 File identity

FileId continuity uses:

1. Explicit paired rename events when the watcher provides reliable pairs.
2. Filesystem identity metadata when portable and available.
3. A unique content-hash match between one removed and one added path in the
   same coalesced batch.
4. New FileId when matching is ambiguous.

Path is unique in the current state but is not the FileId.

### 9.4 DesiredFileState

Parser workers do not mutate the database. They produce an immutable
DesiredFileState:

~~~rust
pub struct DesiredFileState {
    pub file: DesiredFileRecord,
    pub root_spans: Vec<DesiredRootSpan>,
    pub entities: Vec<DesiredEntity>,
    pub source_segments: Vec<DesiredSourceSegment>,
    pub parse_markers: Vec<DesiredParseMarker>,
    pub call_observations: Vec<DesiredCallObservation>,
    pub diagnostics: Vec<FileDiagnostic>,
    pub calculated_accounting: FileAccountingManifest,
}
~~~

Before reconciliation, the state is validated for:

- Source spans within file bounds.
- Root-span non-overlap.
- Complete source-ledger partition.
- Exactly one of InterfaceCode, Comment, or UnknownCode for every segment.
- Comment precedence over RootSpan ownership.
- Interface-code plus comment plus unknown-code bytes equal source bytes.
- Every segment hash matches its immutable source slice.
- Entity containment.
- Observation ownership.
- Source-slice and capture-text equality.
- Unique temporary keys.
- Resource limits.

### 9.5 CaptureChangeSet

Reconciliation compares DesiredFileState with the current stored file state and
produces a CaptureChangeSet:

- File inserts, updates, renames, and deletes.
- Preserved and newly allocated root-span identities.
- Preserved and newly allocated entity identities.
- Removed derived records.
- New source segments.
- New parse markers.
- New call observations.
- Resolution work.
- Search-index work.
- Diagnostics.
- Calculated file and repository accounting manifests.
- Expected prior revision.

The store applies the entire change set in one transaction.

## 10. Daemon and Change Semantics

### 10.1 Startup capture

Startup proceeds as follows:

1. Open and migrate the embedded database.
2. Compile all enabled language packs.
3. Mark capture state as building.
4. Discover the repository using normalized ignore rules.
5. Hash files and compare parser fingerprints.
6. Read each changed file once into an immutable source snapshot.
7. Parse changed or missing files through bounded workers.
8. Construct the three-class ledger and desired states.
9. Calculate file and repository accounting manifests.
10. Reconcile all files, deletions, identities, and calls.
11. Persist the proposed state and independently derive database totals inside
    the transaction.
12. Compare calculated and persisted manifests.
13. Commit one complete initial revision only when every exact invariant passes.
14. Emit the CLI accounting report and mark capture state ready.
15. Start accepting successful graph queries.
16. Start or confirm the filesystem watcher.

The HTTP process may bind earlier, but graph requests return a typed 503
capture_not_ready response until step 13 commits.

### 10.2 Watcher pipeline

Filesystem events are hints, not truth.

The watcher pipeline:

- Receives create, modify, remove, rename, and overflow signals.
- Normalizes repository-relative paths.
- Coalesces repeated events during a short debounce window.
- Preserves delete and rename information.
- Sends one ordered batch to a single capture coordinator.
- Re-stats and re-hashes the filesystem before acting.
- Falls back to a repository reconciliation scan after overflow, uncertainty, or
  restart.

No watcher callback writes to Turso directly. No event spawns an independent
database mutation.

### 10.3 Update transaction

For one coalesced batch:

1. Read current revision R.
2. Discover actual current file states.
3. Parse and validate desired states outside the write transaction.
4. Begin a write transaction expecting revision R.
5. Apply file and entity reconciliation.
6. Remove all derived records for deleted or replaced identities.
7. Re-resolve the required call-observation set.
8. Rebuild affected CallEdge and CallSite rows.
9. Calculate expected byte, class, hash, and row-count totals.
10. Independently query the proposed persisted totals in the same transaction.
11. Compare calculated and persisted manifests and validate database invariants.
12. Set current revision to R + 1.
13. Commit only when every exact comparison passes.

Readers see either revision R or revision R + 1. They never see a half-updated
file or a graph whose incoming and outgoing views disagree.

### 10.4 Delete semantics

Deleting a file must remove:

- Its root spans.
- Its entities.
- Its source segments.
- Its call observations.
- Its call candidates.
- Outgoing call sites and edges.
- Incoming edges whose target no longer exists.
- Search-index records.

Surviving observations elsewhere are re-resolved if the deleted symbols could
have affected their candidate sets.

Foreign-key cascades provide a baseline, but integration tests must prove that
no orphan edge, candidate, site, or search document survives.

### 10.5 Failed update behavior

If parsing, reconciliation, validation, or storage fails:

- The transaction rolls back.
- The prior committed revision remains queryable.
- The failed batch remains pending or is retried according to typed policy.
- Structured diagnostics identify the paths and stage.
- The API reports the last committed revision and degraded capture status when
  appropriate.
- The system does not return an empty collection as a substitute for the error.

Unknown code, malformed source, unresolved calls, and ParseMarker diagnostics do
not by themselves make the transaction invalid. A gap, overlap, hash mismatch,
class-total mismatch, or calculated-versus-persisted row-count mismatch does.

### 10.6 Full rebuild equivalence

For any repository state S:

> capture(empty, S) must be observably equivalent to
> capture(previous_state, event_sequence_to_S)

Observable equivalence covers:

- File statuses.
- Root spans.
- Three-class byte-ledger segments and class totals.
- Parse markers and unknown-code diagnostics.
- Entity descriptors and spans.
- Fuzzy-search ordering.
- Call observations and resolution states.
- Forward edges and call sites.
- Reverse edges and call sites.
- Diagnostics, excluding timestamps and opaque IDs newly allocated after
  genuinely ambiguous reconciliation.

## 11. Turso Persistence Architecture

### 11.1 Why Turso is sufficient

The required graph is relational:

- Entity rows are nodes.
- CallEdge rows are directed edges.
- CallSite rows are edge evidence.
- An index on from_entity_id serves forward calls.
- An index on to_entity_id serves reverse calls.

One-hop adjacency does not require a graph execution engine.

The official Turso Rust SDK supports local embedded databases through the turso
crate. The project is currently described as beta, and its FTS implementation is
experimental. These are external facts, not findings from the local reference
repositories, and must be independently rechecked when implementation begins:

- [Turso Rust quickstart](https://docs.turso.tech/sdk/rust/quickstart)
- [Turso SDK introduction](https://docs.turso.tech/sdk/introduction)
- [Turso Database repository](https://github.com/tursodatabase/turso)
- [Turso FTS documentation](https://docs.turso.tech/sql-reference/functions/fts)
- [Turso code-indexing guide](https://docs.turso.tech/guides/code-indexing)

Mitigation:

- Pin an exact Turso crate version.
- Hide the driver behind narrow store ports.
- Use conservative SQLite-compatible schema features.
- Treat FTS as optional acceleration.
- Maintain crash, reopen, migration, transaction, and backup contract tests.
- Keep the domain independent of Turso row types.

### 11.2 Current-state schema

The schema stores only the current capture. It does not append temporal entity
versions.

Conceptual tables:

| Table | Purpose |
|---|---|
| capture_meta | Repository identity, current revision, readiness, schema and manifest fingerprints |
| capture_accounting | Current revision's calculated and persisted byte, class, and hash manifest |
| capture_relation_counts | Calculated and persisted row counts for every captured relation |
| files | Current file identity, source, status, language, parser fingerprint, and quality |
| root_spans | Non-overlapping file-level ownership envelopes |
| entities | Searchable containers and callables |
| source_segments | Exact gap-free INTERFACE_CODE, COMMENT, and UNKNOWN_CODE accounting |
| parse_markers | Zero-width MISSING nodes and other diagnostics that contain no bytes |
| call_observations | Syntax evidence before and after resolution |
| call_candidates | Ambiguous internal candidates |
| call_edges | Unique resolved internal source-target adjacency |
| call_sites | Observation evidence supporting each edge |
| file_diagnostics | Bounded structured extraction and capture diagnostics |

### 11.4 Source storage

Store source bytes once per supported text file. Entity, root-span, segment, and
call-site records reference byte ranges into that content.

Benefits:

- Exact evidence survives until the next committed revision.
- No duplicated source snippet columns.
- UTF-8 slicing has one implementation.
- API signatures and call-site excerpts can be verified against the source
  hash.
- Tests can reconstruct the complete source ledger from one canonical blob.

Large-file policy may omit source bytes only when the FileRecord explicitly
reports too_large and no entities are published from it.

### 11.5 Calculated-versus-persisted accounting

The capture pipeline reads each file once into an immutable Arc<[u8]>. Parsing,
content hashing, segment hashing, byte classification, and persistence all use
that same snapshot. A pre-read and post-read filesystem check detects a file
that changed while being read; that candidate is discarded and retried.

Before opening the write transaction, the capture layer calculates:

- Source byte totals.
- INTERFACE_CODE, COMMENT, and UNKNOWN_CODE byte totals.
- Ordered per-file ledger hashes.
- File, RootSpan, entity, ParseMarker, call-observation, edge, and call-site
  counts, plus source-segment, candidate, and diagnostic counts.
- A deterministic repository manifest hash over normalized paths, source hashes,
  ledger hashes, and derived-record counts.

After writing the proposed state but before commit, the store independently
queries:

- Length of every persisted source blob.
- Sum of every persisted segment range.
- Sum by the three primary byte classes.
- Persisted row counts for every derived table.
- Segment hashes against their persisted source slices.
- The independently reconstructed manifest hash.

Commit is permitted only when:

~~~text
calculated_source_bytes == persisted_source_bytes

interface_code_bytes + comment_bytes + unknown_code_bytes
    == calculated_source_bytes

calculated_manifest_hash == persisted_manifest_hash

calculated_row_count(table) == persisted_row_count(table)
~~~

capture_relation_counts contains an explicit allowlisted row for files,
root_spans, entities, source_segments, parse_markers, call_observations,
call_candidates, call_edges, call_sites, and file_diagnostics. Adding a captured
relation requires adding it to the manifest contract; an unreported derived
table is a schema test failure.

An exact accounting mismatch is an invariant failure. The transaction rolls
back and the previous revision remains current. A nonzero UNKNOWN_CODE total is
not an invariant failure; it is semantic uncertainty that the CLI reports.

The deep verifier walks persisted rows rather than DesiredFileState objects. For
index --verify it runs against the proposed database state inside the write
transaction, so any mismatch remains rollback-safe. The standalone verify
--deep command reopens the committed database, walks every file and ordered
segment, recomputes all hashes and totals, and compares the reconstructed
manifest with capture_accounting. A later corruption detected by standalone
verification marks the capture unavailable until a clean rebuild succeeds.

### 11.6 Fuzzy-search storage

Correct fuzzy search must not depend on experimental FTS behavior.

The baseline:

1. Query bounded candidates by exact name, exact qualified name, prefix, and
   substring.
2. Rank candidates in Rust using a deterministic scorer.
3. Tie-break by repository-relative path, start byte, and EntityId.

Ranking order:

1. Exact name.
2. Exact qualified name.
3. Name prefix.
4. Qualified-name prefix.
5. Name substring.
6. Token-aware edit or subsequence score.
7. Path and signature match.

An optional Turso FTS n-gram or BM25 index may accelerate candidate generation
after contract tests prove it returns a superset of the required baseline
candidates. Disabling FTS must not change correctness or deterministic ordering.

### 11.7 No Petgraph in the MVP

Petgraph would become useful if the product later requires:

- Multi-hop traversal.
- Strongly connected components.
- Dominators.
- Path enumeration.
- Centrality or clustering.
- In-memory batch graph algorithms.

None is required now. Direct SQL indexes are the simpler and more accurate
implementation for the approved API. The architecture leaves room for a
revision-keyed derived Petgraph snapshot later, but it is neither canonical nor
present in this release.

## 12. Read and API Architecture

### 12.1 Thin HTTP boundary

Axum handlers perform:

1. Request parsing and validation.
2. One call into CurrentGraphQueryService.
3. Typed error mapping.
4. DTO serialization.

Handlers do not contain SQL, ranking rules, source slicing, graph traversal, or
error-swallowing fallbacks.

### 12.2 Response envelope

All successful responses include:

~~~json
{
  "repository_id": "opaque-id",
  "capture_revision": 42,
  "capture_status": "ready",
  "data": {}
}
~~~

The query service begins a read transaction, reads capture_meta, and performs
the query in the same database snapshot. The revision in the response therefore
describes all returned records.

### 12.3 Fuzzy entity search

**GET /code-entities-search-fuzzy?q=...**

Input:

- Required nonblank query.
- Bounded length.
- Optional result limit only if the PRD accepts it as a parameter; otherwise use
  one documented server limit.

Each result includes:

- EntityId.
- Name and qualified name.
- Normalized and language-specific kind.
- Display signature.
- Language.
- Repository-relative path.
- Source span.
- Match class and deterministic score.
- Extraction confidence.

Search does not return raw private implementation bodies. It returns enough
evidence to identify the architecture entity and use its EntityId in a graph
query.

### 12.4 Forward callees

**GET /forward-callees-query-graph?entity=...**

The response includes:

- Root source entity.
- Direct resolved target entities.
- One edge per source-target pair.
- All supporting call-site spans.
- Lexical-context markers.
- Resolution provenance.
- Ambiguous, external, and unresolved observations owned by the source entity in
  a separate evidence collection.

It does not recursively follow returned targets.

### 12.5 Reverse callers

**GET /reverse-callers-query-graph?entity=...**

The response includes:

- Root target entity.
- Direct resolved source entities.
- One edge per source-target pair.
- All supporting call-site spans.
- Resolution provenance.

It does not recursively follow returned sources. Unresolved observations cannot
appear as reverse callers because they do not prove the target.

### 12.6 HTTP semantics

| Condition | Response |
|---|---|
| Valid query, results found | 200 |
| Known entity, no calls | 200 with empty nodes and edges |
| Search query, no match | 200 with empty results |
| Malformed or blank input | 400 |
| Well-formed but unknown EntityId | 404 entity_not_found |
| Initial capture not committed | 503 capture_not_ready |
| Last revision available but daemon degraded | 200 with explicit degraded capture status, if read is sound |
| Database unavailable or snapshot inconsistent | 503 capture_unavailable |
| Internal invariant violation | 500 invariant_violation with diagnostic ID |

No SQL or parser exception text is returned directly to clients.

### 12.7 Determinism

All result sets have explicit ordering:

- Search: score descending, match class, path, start byte, EntityId.
- Forward graph: target qualified name, target path, target start byte,
  EntityId.
- Reverse graph: source qualified name, source path, source start byte,
  EntityId.
- Call sites: path, start byte, observation ID.

Database row order is never treated as API order.

### 12.8 Indexing and accounting CLI

The CLI is a required local product surface. It invokes the same capture,
reconciliation, persistence, and verification services as the daemon; it does
not contain a second indexing implementation.

Required commands:

~~~text
parseltongue index <repository> --verify
parseltongue verify --deep
parseltongue inspect-file <path> --ledger
parseltongue inspect-file <path> --diagnostics
parseltongue capture-report --format table|json
~~~

## 15. Verification Strategy

The architecture is accepted through executable contracts, not through the
presence of modules.

### 15.1 Language-pack contract tests

For every enabled language:

- Grammar loads.
- Every query family compiles.
- Every capture name maps to the typed enum.
- Known root constructs are found.
- Direct members are owned by the expected container.
- Nested local functions are not promoted to peer entities.
- Confirmed comment captures exclude comment-like text inside strings.
- Imports and aliases produce expected hints.
- Call forms produce exact source spans.
- ERROR ranges become UNKNOWN_CODE unless a confirmed comment takes precedence.
- MISSING nodes become zero-width ParseMarkers.
- Unsupported syntax degrades explicitly.

### 15.2 Golden fixture matrix

Each language needs small hand-authored fixtures for:

- Free function calling free function.
- Method calling method.
- Constructor call.
- Same-name symbols in different containers.
- Imported alias.
- External library call.
- Ambiguous call.
- Unresolved dynamic call.
- Nested function or closure call.
- Unicode identifier and string content.
- CRLF source.
- Comments inside and outside RootSpans.
- Comment-like text inside strings.
- Comments-only, whitespace-only, empty, and incomplete files.
- INTERFACE_CODE, COMMENT, and UNKNOWN_CODE accounting.
- Syntax error before and after valid entities.
- File rename and entity line shift.

Goldens assert domain records and source excerpts. They should not be generated
from the implementation under test and accepted without review.

### 15.3 Source-ledger property tests

For arbitrary valid byte sequences accepted as text:

- Segments sort into [0, N).
- No gap exists.
- No overlap exists.
- Every segment has exactly one of the three primary classes.
- Confirmed comments take precedence over RootSpan ownership.
- Interface-code bytes plus comment bytes plus unknown-code bytes equal N.
- Concatenating segment slices recreates the original source bytes.
- Every segment hash matches its source slice.
- Direct member overlays do not increase byte totals.
- ERROR and dangling regions remain present as UNKNOWN_CODE.
- Zero-width ParseMarkers do not alter byte totals.
- Every segment range is UTF-8-boundary-safe when converted to text.
- Every entity and observation span is within bounds.

### 15.4 Graph invariants

Tests prove:

- Every edge has at least one call site.
- Every call site references a resolved observation.
- Every edge endpoint exists.
- Forward and reverse lookups return the same edge set viewed from opposite
  indexes.
- Ambiguous observations do not create edges.
- External observations do not create internal targets.
- Deleting a target removes incoming edges.
- Reintroducing a uniquely matching target re-resolves affected observations.

### 15.5 Identity tests

Scenarios:

- Insert blank lines before an unchanged function: preserve EntityId.
- Add comments above an unchanged method: preserve EntityId.
- Move a function within the same file uniquely: preserve EntityId.
- Rename a file with unchanged content: preserve FileId and EntityId when the
  rename match is unique.
- Rename a function: policy-defined new or preserved identity based on unique
  structural evidence, with the decision tested.
- Duplicate an identical function: never force one old identity onto two new
  entities.
- Swap two same-named similar functions: ambiguous reconciliation allocates new
  identity rather than guessing.

### 15.6 Daemon integration tests

Use temporary fixture repositories and real filesystem operations:

- Initial capture.
- Create file.
- Modify file.
- Atomic-save rename pattern.
- Delete file.
- Rename file.
- Burst of repeated writes.
- Watcher overflow simulation.
- Process restart between event and commit.
- Parse failure during update.
- Incomplete source that still commits with UNKNOWN_CODE.
- Accounting mismatch that rolls back the proposed revision.
- Database failure during update.
- Ignore-file change.
- Language-manifest fingerprint change.

Every scenario compares the final state with a clean rebuild.

### 15.7 Turso adapter contract tests

Required:

- Migration from empty database.
- Reopen persisted database.
- Commit and rollback.
- Reader sees old snapshot during uncommitted update.
- Reader sees new revision after commit.
- Foreign-key and orphan cleanup behavior.
- Calculated source bytes equal persisted source-blob lengths.
- Three-class totals equal persisted source bytes.
- Calculated and persisted row counts match.
- Segment hashes match persisted source slices.
- Manifest mismatch rolls back the transaction.
- Concurrent read and serialized write.
- Interrupted process recovery.
- Backup or copy behavior.
- FTS-disabled fuzzy-search correctness.
- Optional FTS candidate parity if FTS is enabled.

These tests are especially important because the selected Rust driver is beta.

### 15.8 API contract tests

Tests enumerate the router and prove it has exactly three public routes.

For each route:

- Success shape.
- Empty shape.
- Invalid input.
- Unknown entity.
- Capture not ready.
- Capture degraded.
- Store unavailable.
- Deterministic ordering.
- Revision consistency.
- Result-size enforcement.

### 15.9 CLI contract tests

Tests prove:

- Index output reports the committed capture revision.
- Human-readable byte and row totals reconcile exactly.
- JSON output uses a stable versioned schema and deterministic ordering.
- File inspection returns ordered ledger ranges and diagnostic reasons.
- Deep verification reconstructs source and independently recalculates the
  manifest.
- Deliberate corruption of source bytes, ranges, classes, segment hashes, or row
  counts is detected.
- UNKNOWN_CODE is visible but does not become an accounting failure.
- No CLI command registers an additional HTTP route.

### 15.10 Fuzzing and replay

Fuzz:

- Random source edits.
- Byte and character coordinate conversion.
- Source-ledger interval construction.
- Comment-range precedence and overlapping semantic spans.
- Calculated-versus-persisted manifest reconciliation.
- Tree traversal depth and malformed trees.
- Event coalescing sequences.
- Reconciliation matching.

Persist minimal failing edit sequences as regression fixtures. Full rebuild is
the oracle for incremental reconciliation.

### 15.11 Benchmarks

Benchmark the pipeline, not only Tree-sitter:

- Repository discovery.
- Hash gate.
- Parse by language and file size.
- Root and entity extraction.
- Source-ledger construction.
- Segment hashing and manifest calculation.
- Deep committed-database verification.
- Call observation extraction.
- Local and global resolution.
- Reconciliation.
- Turso transaction.
- Fuzzy candidate generation and ranking.
- Forward and reverse read latency.
- Startup reopen without reparse.

Performance targets should be set only after representative repositories and
hardware are selected. This document does not invent latency claims.

## 16. Migration as a Complete Rewrite

The index is derived from source, so migrating old Cozo rows is more dangerous
than rebuilding them. The rewrite should run side by side until verified.

### 16.1 Delivery sequence

#### Phase 0: Freeze product contracts

- Turn the narrowed PRD into API and capture acceptance tests.
- Select multilingual fixture repositories.
- Record current-route behavior only where it remains desired.
- Define the exact three response schemas.
- Define the versioned CLI accounting-report schema.

#### Phase 1: Build the pure domain

- Add identity and span newtypes.
- Add RootSpan, AddressableEntity, SourceSegment, and call evidence models.
- Add the three SourceByteClass values, ParseMarker, and accounting manifests.
- Implement invariant validators.
- Write source-ledger and graph property tests.

#### Phase 2: Port the CodeMogger-shaped capture core

- Add central language manifest.
- Add parser workers and query-family loading.
- Implement root-child extraction.
- Implement member extraction.
- Implement confirmed-comment extraction and exact three-class source
  accounting.
- Produce DesiredFileState without persistence.

#### Phase 3: Add call evidence and resolution

- Extract observations.
- Build scope and import hints.
- Implement conservative resolution states.
- Prove forward and reverse edge symmetry.

#### Phase 4: Add Turso current-state storage

- Create migrations.
- Implement narrow read and write ports.
- Implement calculated-versus-persisted accounting queries.
- Add transactional revision publication.
- Add crash, reopen, and cleanup tests.

#### Phase 5: Add reconciliation and daemon

- Implement stable identity matching.
- Add initial scan.
- Add watcher event coalescing.
- Add delete and rename semantics.
- Add clean-rebuild parity tests.

#### Phase 6: Replace the HTTP surface and add the CLI

- Implement the three handlers.
- Add deterministic DTOs and typed errors.
- Prove route count.
- Implement index, verify, inspect-file, and capture-report commands over shared
  capture services.
- Add deterministic table and versioned JSON accounting output.
- Keep old server available only as a local rollback binary during acceptance.

#### Phase 7: Cut over

- Build a fresh Turso index from source.
- Run language goldens and fixture repositories.
- Compare incremental and clean captures.
- Switch the default binary.
- Remove Cozo, temporal models, broad routes, and obsolete handlers.
- Update README examples to use opaque EntityId values from fuzzy search.

### 16.2 No data migration

Do not translate old Cozo rows into the new schema. Reasons:

- Existing line-derived and synthetic temporal identities do not satisfy the new
  identity contract.
- Existing edge resolution is not strong enough to inherit as fact.
- Source is the authoritative data.
- A fresh parse is simpler to audit.

The old database can be retained temporarily for rollback and comparison, then
deleted after acceptance.

### 16.3 Cutover gates

Cutover requires:

- All language packs compile and pass contracts.
- Exact three-class source-ledger properties pass.
- Confirmed comments are separate from interface-code bytes.
- Calculated and persisted manifests match.
- Deep verification detects deliberate ledger and database corruption.
- CLI table and JSON accounting contracts pass.
- All three API contracts pass.
- Router exposes no extra public route.
- Empty calls return 200.
- Storage failures do not return empty success.
- Delete and rename integration tests pass.
- Incremental state equals clean rebuild on selected fixture repositories.
- Turso crash and reopen tests pass.
- Representative repository performance is documented.
- The README matches the implemented product.

## 17. Risks and Countermeasures

| Risk | Consequence | Countermeasure |
|---|---|---|
| Turso Rust driver is beta | Driver behavior or API may change | Pin version, isolate adapter, use contract tests, avoid proprietary features in the canonical schema |
| Turso FTS is experimental | Search behavior may drift | Keep deterministic Rust ranking and non-FTS candidate fallback |
| Grammar drift | Queries stop compiling or captures silently change | Version language packs, compile at startup, maintain goldens, include query hash in cache fingerprint |
| Query fragility | Missing or overbroad entities and calls | Separate query families, typed captures, language-specific refiners, capture-count limits |
| Comment misclassification | Comment bytes are counted as interface or unknown code | Dedicated comments.scm contracts, string-literal counterexamples, comment-precedence goldens |
| Dynamic-language resolution | False call edges | Preserve ambiguous/external/unresolved states; prefer missing edge to false certainty |
| Overloads and dispatch | Wrong unique target | Use signatures and context only when proven; retain candidates; do not emulate a compiler casually |
| Watcher drops or reorders events | Stale current graph | Treat events as hints, single writer, content recheck, overflow full scan, clean-rebuild parity |
| Entity matching guesses continuity | Evidence attributed to wrong entity | Confidence ladder; allocate a new ID on ambiguity |
| Global re-resolution is slow | Update latency grows with repository | Trigger only for symbol-surface changes; benchmark; add dependency-key optimization later with parity tests |
| Source ledger increases storage | Larger embedded database | Store source once, use compact integer spans, benchmark; do not duplicate snippets |
| Manifest verification increases indexing time | Initial capture or updates take longer | Hash immutable source once, verify incrementally per changed file, retain deep whole-repository verification as an explicit CLI mode |
| UNKNOWN_CODE is mistaken for data loss | Users distrust an otherwise exact capture | Report accounting and semantic results separately; always expose unknown ranges and reasons |
| Tree-sitter parser memory | High peak memory on large repos | Bounded worker pool, source-size limits, drop trees after extraction |
| Malformed or generated files | Resource exhaustion or noisy graph | Time, depth, capture, file-size, and diagnostic limits with explicit status |
| Nested-call ownership is misunderstood | User interprets lexical edge as runtime execution | Return lexical-context evidence and document graph semantics |
| Full current-state only | No historical comparison | Deliberate PRD decision; avoid designing hidden temporal machinery |
| Complete rewrite scope | Migration risk | Side-by-side build, executable gates, fresh source reindex, old binary rollback until acceptance |

## 18. Architecture Decisions

### ADR-001: CodeMogger is the primary blueprint

**Decision:** Adopt CodeMogger's central language mapping, root-child parsing,
parser reuse, current-index pipeline, and Turso precedent.

**Reason:** It starts from the simplest architecture that matches the reduced
product.

**Modification:** Add stable identity, exact source ledger, addressable members,
call observations, conservative resolution, and atomic revision publication.

### ADR-002: Turso is the canonical current-state store

**Decision:** Persist files, entities, evidence, and edges in embedded Turso.

**Reason:** Transactions and indexed relational adjacency are sufficient for the
three required APIs.

**Constraint:** Domain and query contracts remain backend-neutral behind narrow
ports.

### ADR-003: No Petgraph in the first release

**Decision:** Query forward and reverse one-hop adjacency directly in SQL.

**Reason:** Petgraph would duplicate state without serving a current product
requirement.

### ADR-004: Root spans own top-level architecture

**Decision:** Direct semantic children of a file form non-overlapping RootSpans.
Direct callable members remain addressable child entities. Nested locals and
closures remain owned by the nearest callable.

**Reason:** This balances a low-noise architecture view with useful call
precision.

### ADR-005: Identity is opaque and reconciled

**Decision:** Use store-assigned UUIDv7 identity. Use descriptors, fingerprints,
and locations only as reconciliation evidence.

**Reason:** Lines, paths, names, and content all change independently.

### ADR-006: Calls are evidence first

**Decision:** Persist syntax observations before target resolution. Create edges
only for accepted internal targets.

**Reason:** The system must expose uncertainty and avoid false graph facts.

### ADR-007: Incremental means desired-state reconciliation

**Decision:** Skip unchanged files, fully reparse changed files, reconcile
desired state, and atomically publish.

**Reason:** This captures most practical incremental value without the
correctness burden of Tree-sitter InputEdit handling.

### ADR-008: Tree-sitter edit reuse is deferred

**Decision:** Do not retain old trees or apply incremental edits in the first
release.

**Reason:** File-system events rarely provide exact byte and point edits, and
full-file parsing is a simpler correctness baseline. Add edit reuse only after
fuzzed parity tests exist.

### ADR-009: The graph is lexical and one-hop

**Decision:** A call edge means current source owned by entity A contains a
resolved call observation to entity B. It does not prove runtime execution.

**Reason:** This is the strongest backend-neutral claim the parser can make
across all target languages without full compilation.

### ADR-010: Exactly three public APIs

**Decision:** The router exposes fuzzy search, forward callees, and reverse
callers only. Indexing, verification, ledger inspection, and capture reports are
CLI commands, not HTTP routes.

**Reason:** Product focus is a feature. Internal diagnostics do not become
public product surface by default.

### ADR-011: The byte ledger has exactly three classes

**Decision:** Every captured byte is classified exactly once as INTERFACE_CODE,
COMMENT, or UNKNOWN_CODE. Confirmed comments take precedence over RootSpan
ownership. Member entities are overlays and do not add bytes.

**Reason:** A small mutually exclusive classification makes exact accounting
auditable across languages while preserving incomplete and unsupported source.

### ADR-012: Unknown is allowed; accounting mismatch is not

**Decision:** UNKNOWN_CODE and parser diagnostics may be committed. A gap,
overlap, source mismatch, segment-hash mismatch, class-total mismatch, or
calculated-versus-persisted record mismatch aborts publication.

**Reason:** Semantic uncertainty is expected in live code. Losing or
double-counting source is a correctness failure.

### ADR-013: Indexing emits an auditable CLI result

**Decision:** The shared capture pipeline produces deterministic table and JSON
reports comparing calculated and persisted bytes, classes, hashes, and row
counts.

**Reason:** Users need visible proof of what entered the database and what
remained unknown without expanding the HTTP API.

## 19. Rejected Designs

### 19.1 Neo4j-backed service

Rejected because the deployment and query-language surface exceed the need.
One-hop adjacency does not justify a server graph database.

### 19.2 Cozo temporal graph

Rejected because history and Datalog are outside the narrowed PRD. The old model
also encourages temporal identity concepts that complicate a current-state
capture.

### 19.3 Turso plus always-hydrated Petgraph

Rejected for the first release because it creates dual representations and
cache invalidation. It can be revisited for proven multi-hop algorithms.

### 19.4 CocoIndex retrieval chunks as graph nodes

Rejected because overlapping token-budget chunks are not stable architecture
entities.

### 19.5 Content hash as EntityId

Rejected because a body edit would create a new identity, identical code could
collide semantically, and moves or duplication become ambiguous.

### 19.6 Path and line span as EntityId

Rejected because insertion, formatting, and renames move lines without changing
the logical entity.

### 19.7 Recursive extraction of every nested function

Rejected because it flattens lexical ownership, produces graph noise, and
misrepresents nested implementation details as peer public architecture.

### 19.8 Keep stale entities on parse failure

Rejected because a successful response would describe source that no longer
exists. The correct behavior is an explicit degraded capture with current
evidence only.

### 19.9 One watcher task per event

Rejected because event order, deletion, rename pairing, and atomic revision
publication become nondeterministic.

### 19.10 Fine-grained primary byte classes

Rejected because classes such as whitespace, delimiter, import, parse error,
directive, and invalid encoding make the accounting contract language-dependent
and brittle. Those remain semantic roles or diagnostic reasons. Only confirmed
comments deserve their own universal class; every non-interface residual is
UNKNOWN_CODE.

## 20. End-State Blueprint

When the rewrite is complete, a user should experience this sequence:

1. Start Parseltongue against one repository.
2. The daemon discovers every relevant file and compiles enabled language packs.
3. Each changed file is read into one immutable source snapshot.
4. The file is parsed into root spans, addressable entities, confirmed comments,
   call observations, and a gap-free three-class byte ledger.
5. The reconciler preserves identities where evidence is strong and creates new
   identities where it is not.
6. The resolver creates only evidence-backed internal call edges.
7. The capture layer calculates source, class, hash, and row-count manifests.
8. Turso persists the proposed state and independently derives the same totals.
9. The revision commits only when both manifests match.
10. The CLI reports interface-code, comment, and unknown-code bytes plus all
    calculated-versus-persisted record counts.
11. Fuzzy search returns stable EntityId values with signatures and source spans.
12. Forward lookup returns direct resolved callees plus unresolved evidence.
13. Reverse lookup returns direct proven callers.
14. A filesystem edit is coalesced, reparsed, reconciled, re-resolved, validated,
    and committed as the next revision.
15. Queries during the update continue to see the prior consistent revision.
16. A clean rebuild produces the same observable result.

The architecture is intentionally modest in public surface and demanding in
internal correctness. That is the right trade for the product thesis. The user
does not need another general code index. The user needs a small graph they can
believe.

## 22. Final Architectural Thesis

Parseltongue should not compete by becoming a larger graph system. It should
compete by making a very small graph unusually trustworthy.

CodeMogger supplies the right skeleton: explicit language mappings,
Tree-sitter-driven root extraction, current-state indexing, and embedded Turso.
CocoIndex contributes richer coordinates and a reconciliation mindset.
Parseltongue's contribution is the Root-Span Call Graph:

- one file,
- one layer of root ownership,
- direct callable members where call precision requires them,
- exact INTERFACE_CODE, COMMENT, and UNKNOWN_CODE accounting,
- calculated-versus-persisted verification through the CLI,
- opaque durable identity,
- evidence before edges,
- explicit uncertainty,
- atomic current revisions,
- direct forward and backward calls,
- and one fuzzy doorway into the graph.

That is enough architecture to support the product, and little enough product
surface to make correctness achievable.
