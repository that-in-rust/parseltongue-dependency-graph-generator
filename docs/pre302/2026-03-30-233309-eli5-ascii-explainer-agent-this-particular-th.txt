⏺ This is a great question, and your archived research already has the answer —
  yes, definitively yes. Here's the synthesis:

  The Short Answer

  Rust's compiler gives you exact, compiler-verified control flow via MIR. Not
  approximate. Not heuristic. Exact. This is fundamentally different from
  tree-sitter.

  What You Already Decided (and it was right)

  Your archived docs show converged decisions on this:

  ┌───────────┬──────────────────┬──────────────────────────────────────────┐
  │   Layer   │       Tool       │            What It Gives You             │
  ├───────────┼──────────────────┼──────────────────────────────────────────┤
  │ Syntax    │ tree-sitter      │ Declarations, line ranges, basic         │
  │           │                  │ patterns (all languages)                 │
  ├───────────┼──────────────────┼──────────────────────────────────────────┤
  │ Semantics │ rustc_private +  │ Exact call graphs, CFG, type resolution, │
  │           │ MIR              │  trait dispatch (Rust only)              │
  ├───────────┼──────────────────┼──────────────────────────────────────────┤
  │ Ownership │ Polonius facts   │ Move semantics, borrow lifecycle,        │
  │           │                  │ liveness at every CFG point              │
  └───────────┴──────────────────┴──────────────────────────────────────────┘

  Why MIR Solves Your Control Flow Problem

  MIR (Mid-level IR) gives you the literal control flow graph the compiler uses:

  ┌──────────────────────────────────────────────────────────┐
  │  MIR Body                                                │
  │                                                          │
  │  bb0: ──→ bb1 (if condition)                             │
  │       ──→ bb3 (else)                                     │
  │                                                          │
  │  bb1: ──→ bb2 (call foo())                               │
  │                                                          │
  │  bb2: ──→ bb4 (return)                                   │
  │                                                          │
  │  bb3: ──→ bb4 (call bar())                               │
  │                                                          │
  │  bb4: ──→ return                                         │
  │                                                          │
  │  APIs:                                                   │
  │    body.basic_blocks          → all blocks                │
  │    block.successors()         → forward edges             │
  │    basic_blocks.predecessors()→ backward edges            │
  │    basic_blocks.dominators()  → dominator tree            │
  │    TerminatorKind::Call       → exact call targets        │
  │    Instance::try_resolve()    → resolves trait → concrete │
  └──────────────────────────────────────────────────────────┘

  The killer feature: Instance::try_resolve() solves the exact problem your
  thesis identified as the biggest constraint — "tree-sitter knows foo() calls
  bar() but not which bar()." MIR resolves trait dispatch to the concrete 
  implementation. No ambiguity. No "3 possible targets." The compiler knows.

  What This Means for Your Control Flow Diagrams

  You can produce fully deterministic, predictable control flow diagrams
  because:

  1. CFG is a DAG of BasicBlocks — each block has typed successors (branch,
  call, drop, return, panic)
  2. Call graph is fully resolved — direct calls, trait dispatch, generic
  monomorphization, closures
  3. Dominator tree is built-in — BasicBlocks::dominators() gives you loop
  detection, unreachable code
  4. Data flow is available — MaybeInitializedPlaces, MaybeLiveLocals, variable
  def/use chains

  So the flow from codebase → diagram looks like:

  Rust source
      │
      ▼ (rustc_private, pinned nightly)
  MIR basic blocks + terminators
      │
      ▼ (extract TerminatorKind::Call, Branch, Drop)
  Control Flow Graph (exact, typed edges)
      │
      ▼ (Instance::try_resolve for trait dispatch)
  Resolved Call Graph (no ambiguity)
      │
      ▼ (Leiden clustering on the call graph)
  Community-grouped control flow diagram

  The Clustering Question

  Your research on Leiden is spot-on. Once you have the exact call graph from
  MIR (not tree-sitter's approximate one), Leiden clustering becomes
  dramatically more meaningful — because the edges are real. Your modularity > 
  0.3 gate works because the graph isn't polluted with false edges.

  What's Different from Tree-Sitter

  ┌────────────────────────┬────────────────────┬───────────────────────────┐
  │       Capability       │    tree-sitter     │         rustc MIR         │
