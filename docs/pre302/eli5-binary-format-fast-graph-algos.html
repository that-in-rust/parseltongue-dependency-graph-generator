Why ISG Binary Makes Graph Algorithms Scream

An ELI5 explanation of how mmap'd dense arrays + sorted edge lists turn a 50K-entity code graph into a playground for BFS, PageRank, Leiden, k-core, SCC, and PPR -- and why SQLite can't keep up.

Level 1 -- The Essence

The ISG binary format turns your code graph into a flat array that the CPU can chew through like a straight highway -- no stoplights (SQL parsing), no roundabouts (hash lookups), no toll booths (deserialization). The whole graph fits in L3 cache (11.7 MiB), so every algorithm runs at memory speed, not disk speed.

The Core Idea 
           SQLite / JSON                    ISG Binary
     ________________________        ________________________
    |                        |      |                        |
    |  SELECT * FROM edges   |      |  entity N = ptr[N*64]  |
    |  WHERE src = 42        |      |  edges = ptr[start..   |
    |                        |      |           start+count]  |
    |  1. Parse SQL string   |      |                        |
    |  2. B-tree traverse    |      |  1. Multiply           |
    |  3. Deserialize rows   |      |  2. Read bytes         |
    |  4. Alloc Vec<Edge>    |      |  Done.                 |
    |  5. Return copy        |      |  Zero alloc. Zero copy.|
    |________________________|      |________________________|
    |                        |      |                        |
    |  ~50 us per lookup     |      |  ~0.5 us per lookup    |
    |  (100x slower)         |      |  (CPU cache speed)     |
    |________________________|      |________________________|

Think of it this way: SQLite is a library with a librarian. You ask for a book, she walks to the shelf, looks up the index, finds the book, photocopies it, and hands you the copy. ISG is an open bookshelf where book #42 is always at slot #42. You just reach and grab it. No librarian. No photocopy.

Level 2 -- The 5 Foundations That Make It Fast

Before we look at each algorithm, here are the five tricks that the ISG binary format uses. Every algorithm benefits from all five.

Foundation 1: Dense Arrays -- "Entity N lives at byte N*64"

The key insight: when your ID IS your index, lookup is just multiplication. No hash table. No B-tree. No binary search. Multiply and read.

ZOOMING IN -- Dense Array Layout 
  entities.idx  (mmap'd file, 64 bytes per entry)
  _______________________________________________
 |      |      |      |      |      |      |     |
 | E[0] | E[1] | E[2] | E[3] | E[4] | E[5] | ...|
 |______|______|______|______|______|______|_____|
 ^      ^      ^      ^
 |      |      |      |
byte 0  64    128    192

 "Where is entity 42?"

   Answer: byte 42 * 64 = byte 2688
   Cost: ONE multiplication. Done.

 Compare to SQLite B-tree:
 ____________________________
|         Root Page          |
|  keys: [100, 500, 900]    |
|    /       |       \       |
|  Page2   Page5   Page8     |  <-- 3-4 page reads
|  /    \                    |      to find entity 42
| Leaf   Leaf                |
|  [38,39,40,41,>>42<<,43]  |  <-- then deserialize row
|____________________________|

Dense array: O(1) with a single multiply. B-tree: O(log N) with 3-4 random page reads. For 50K entities, that's ~16 comparisons and ~4 page faults vs. 1 multiply.

Foundation 2: mmap -- "The OS Does the Caching for Free"

mmap maps the file directly into your process's virtual address space. The OS page cache handles loading pages from disk. Your code just reads pointers. No read() syscalls. No application-level cache. No double-buffering.

ZOOMING IN -- mmap vs. Traditional I/O 
  TRADITIONAL (SQLite):
  ______        ________        ___________
 | Disk | ───> | Kernel | ───> | App Buffer|
 |      | read |  Page  | copy |  (malloc) |
 |______|      | Cache  |      |___________|
                                     |
                                  parse SQL
                                  build rows
                                  return Vec

  Two copies. Syscall overhead. Allocation.

  ──────────────────────────────────────

  MMAP (ISG):
  ______        ____________________________
 | Disk | ───> |  Kernel Page Cache         |
 |      | lazy |                            |
 |______|      |  Your process's address    |
               |  space. Just a pointer.    |
               |  entities[42] = THIS byte. |
               |____________________________|

  Zero copies. No syscall after initial mmap.
  OS prefetches pages automatically.

When you access entities[42], the OS checks if that page is in RAM. If yes: instant (nanoseconds). If no: one page fault, load 4 KiB from SSD (~10 us), then cached forever. After a full scan, the entire 11.7 MiB file is in RAM and every access is at L3 cache speed.

Foundation 3: Sorted Contiguous Edges -- "All neighbors in a row"

This is the big one for graph algorithms. In edges.fwd, all outgoing edges for entity N are stored in a contiguous block. You don't search for them -- you just read bytes [start..start+count].

ZOOMING IN -- Edge Layout for BFS 
  edges.fwd  (sorted by src_seq, 12 bytes per edge)
  ___________________________________________________
 |E0's edges  |E1's edges     |E2's  |E3's edges    |
 |a b c       |d e f g h      |i     |j k l m n o   |
 |____________|_______________|______|______________|
  ^                            ^
  |                            |
  Entity 0 has 3 outgoing     Entity 2 has 1 outgoing
  edges starting at index 0    edge starting at index 8

  Entity 2's offset table entry:
  ┌────────────────────────┐
  │ start = 8, count = 1   │  <-- O(1) lookup
  └────────────────────────┘
  So: edges_fwd[8..9] = one 12-byte read. Done.

  Compare to SQLite:
  ┌───────────────────────────────────┐
  │ SELECT * FROM edges              │
  │ WHERE src_id = 'rust:fn:main'    │
  │ ORDER BY dst_id;                 │
  │                                   │
  │ 1. Parse SQL                      │
  │ 2. Plan query                     │
  │ 3. Walk B-tree index on src_id    │
  │ 4. For each match, read row page  │
  │ 5. Deserialize each row           │
  │ 6. Alloc result vector            │
  │ 7. Sort results                   │
  │ 8. Return                         │
  └───────────────────────────────────┘

Contiguous = the CPU prefetcher sees you reading bytes 96, 108, 120 and pre-loads 132, 144, 156 before you even ask. B-tree rows are scattered across different pages -- no prefetching possible.

Foundation 4: Cache Locality -- "11.7 MiB fits in L3"

Apple M-series chips have ~24 MiB of L3 cache. The entire ISG graph (11.7 MiB) fits inside it. After one full scan, every subsequent access hits L3 cache (~5 ns) instead of main RAM (~50 ns) or SSD (~10,000 ns).

DEEP DIVE -- The Memory Hierarchy 
                            Access Time
  ┌──────────────┐
  │   L1 Cache   │  ~1 ns     64 KiB     1 entity entry
  │  (per core)  │                        fits perfectly
  ├──────────────┤                        (64 bytes = 1
  │   L2 Cache   │  ~3 ns     ~4 MiB     cache line)
  │  (per core)  │
  ├──────────────┤
  │   L3 Cache   │  ~5 ns     ~24 MiB  <-- ENTIRE ISG
  │  (shared)    │                         GRAPH FITS
  │              │                         HERE (11.7 MiB)
  ├──────────────┤
  │  Main RAM    │  ~50 ns    16+ GiB     SQLite page cache
  │  (DRAM)      │                         lives here
  ├──────────────┤
  │     SSD      │  ~10 us    512+ GiB    SQLite DB file
  │              │  (10,000 ns)            lives here
  └──────────────┘

  ISG: everything at 5 ns
  SQLite: bounces between 50 ns and 10,000 ns
  That's 10x to 2000x slower per access.

Foundation 5: Zero Allocation -- "&[EdgeEntry] not Vec<Edge>"

When you query SQLite, it allocates a Vec, copies each row into a struct, and hands you owned data. ISG gives you a slice pointing directly into the mmap'd file. No alloc. No copy. No destructor.

ZOOMING IN -- Allocation Cost 
  SQLite: "give me entity 42's edges"
  ┌─────────────────────────────────────────┐
  │ let edges: Vec<Edge> = db.query(...);  │
  │                                         │
  │ Internally:                             │
  │   1. malloc(N * sizeof(Edge))  ~50 ns   │
  │   2. for each row:                      │
  │      - parse blob        ~200 ns        │
  │      - copy into Vec      ~10 ns        │
  │   3. When done: free(edges)  ~30 ns     │
  │                                         │
  │ Total overhead per query: ~500 ns+      │
  │ Garbage pressure: YES                   │
  └─────────────────────────────────────────┘

  ISG: "give me entity 42's edges"
  ┌─────────────────────────────────────────┐
  │ let edges: &[EdgeEntry] =              │
  │     &fwd[start..start + count];        │
  │                                         │
  │ Internally:                             │
  │   1. Pointer add.  ~0.3 ns              │
  │   That's it.                            │
  │                                         │
  │ Total overhead per query: ~0.3 ns       │
  │ Garbage pressure: ZERO                  │
  └─────────────────────────────────────────┘

This matters enormously for algorithms like PageRank that iterate ALL edges 20-50 times. 200K edges * 50 iterations = 10 million edge reads. At 500 ns overhead each for SQLite, that's 5 entire seconds of pure overhead. ISG: 3 ms of pure overhead (pointer adds).

Level 3 -- Algorithm-by-Algorithm Deep Dive

1
BFS -- Breadth-First Search

Used for: call chain explorer, blast radius, neighborhood discovery. "Show me everything within 3 hops of main()."

Access pattern: Start at one node. Visit all neighbors. Then visit THEIR neighbors. Repeat for N hops. The critical operation is "give me all neighbors of node X" -- and you do it once per node you visit.

ZOOMED OUT -- BFS Walks the Graph 
  Start: entity 42 (main)

  Hop 0:  [42]

  Hop 1:  [42] ───> [7, 15, 88]
                     neighbors of 42

  Hop 2:  [7]  ───> [3, 21]
          [15] ───> [42, 99]     (42 already visited, skip)
          [88] ───> [15, 200]    (15 already visited, skip)

  Result: {42, 7, 15, 88, 3, 21, 99, 200}
          blast radius = 8 entities in 2 hops

The critical inner loop: for each entity we visit, we need to read its outgoing edges. This is where ISG destroys SQLite.

DEEP DIVE -- BFS Neighbor Read 
  ISG -- visiting entity 42:

  Step 1: Read offset table              Cost
  ┌──────────────────────────┐
  │ off = fwd_off[42]       │  8 bytes, O(1)
  │ off.start = 1050        │  ptr + 42*8 = ptr + 336
  │ off.count = 7           │
  └──────────────────────────┘

  Step 2: Read contiguous edge block
  ┌──────────────────────────────────────┐
  │ edges_fwd[1050..1057]               │
  │ ┌────┬────┬────┬────┬────┬────┬────┐│
  │ │e[0]│e[1]│e[2]│e[3]│e[4]│e[5]│e[6]││
  │ │12B │12B │12B │12B │12B │12B │12B ││
  │ └────┴────┴────┴────┴────┴────┴────┘│
  │  84 bytes, CONTIGUOUS in memory     │
  │  CPU prefetcher loads them all      │
  └──────────────────────────────────────┘

  Step 3: For each edge, just read dst_seq (4 bytes)
  ┌────────────────┐
  │ edge.dst_seq   │  the neighbor's ID
  │ Already in the │  No string lookup needed
  │ 12-byte entry  │  during BFS traversal
  └────────────────┘

  Total per node: ~100 bytes read, ~10 ns

  ──────────────────────────────────────────

  SQLite -- visiting entity 42:

  Step 1: Send SQL query
  ┌──────────────────────────────────────┐
  │ SELECT dst_id FROM edges            │
  │ WHERE src_id = 'rust:fn:main';      │
  │                                      │
  │ Cost: SQL parse         ~5 us       │
  │       Query plan        ~2 us       │
  │       B-tree walk       ~3 us       │
  │       Row deserialize   ~5 us       │
  │       Vec allocation    ~0.5 us     │
  └──────────────────────────────────────┘

  Total per node: ~15 us (15,000 ns)

BFS on ISG: ~10 ns per node visited (1500x faster). A 2-hop BFS visiting 500 nodes: ISG = 5 us. SQLite = 7.5 ms.

ISG Binary ~5 us

BFS 2-hop from entity 42:
  500 nodes visited
  x 10 ns each (contiguous read)
  = ~5 us total

  Allocations: 0
  Syscalls: 0
  Cache misses: ~10
  (edges are contiguous)

SQLite ~7.5 ms

BFS 2-hop from entity 42:
  500 nodes visited
  x 15 us each (SQL per node)
  = ~7.5 ms total

  Allocations: 500
  Syscalls: ~500
  Cache misses: ~2000
  (B-tree pages scattered)
2
PageRank -- Entity Importance Ranking

Used for: "Which functions are the most important in this codebase?" Ranks every entity by how many important things depend on it.

Access pattern: FULL SEQUENTIAL SCAN of all edges, repeated 20-50 times. For each edge, read source score, divide by out-degree, add to destination score. This is the most I/O-intensive algorithm.

ZOOMED OUT -- PageRank Iteration 
  Round 1 of 30:

  scores_new = [0.0; 50_000]    (one f32 per entity)

  For EVERY edge (src, dst) in edges.fwd:
    ┌───────────────────────────────────────┐
    │ contribution = scores[src]            │
    │              / out_degree[src]         │
    │ scores_new[dst] += contribution       │
    └───────────────────────────────────────┘

  Repeat 30 times until convergence.

  Total edge reads: 200K edges x 30 rounds = 6 million

Why sequential scan is everything: PageRank reads every single edge in order. This is the dream scenario for contiguous arrays -- the CPU prefetcher sees the sequential pattern and loads the next cache line before you even ask for it.

DEEP DIVE -- Sequential Scan Magic 
  ISG edges.fwd: 200K entries x 12 bytes = 2.3 MiB
  Laid out in memory:

  ┌──────┬──────┬──────┬──────┬──────┬──────┐
  │edge 0│edge 1│edge 2│edge 3│edge 4│edge 5│...
  │ 12B  │ 12B  │ 12B  │ 12B  │ 12B  │ 12B  │
  └──────┴──────┴──────┴──────┴──────┴──────┘
   ▲                     ▲
   │ CPU reads here      │ Prefetcher already
   │ right now           │ loaded this cache line

  The CPU prefetcher detects: "they're reading
  sequentially!" and loads AHEAD of you.

  Result: effectively ZERO cache misses for
  the edge scan. Pure memory bandwidth.

  M-series memory bandwidth: ~100 GB/s
  2.3 MiB / 100 GB/s = 0.023 ms per round
  30 rounds = 0.7 ms for ALL edge I/O

  ──────────────────────────────────────────

  SQLite: has to iterate via cursor

  ┌────────────────────────────────────────┐
  │ SELECT src_id, dst_id FROM edges;     │
  │                                        │
  │ For each of 200K rows:                │
  │   - Advance B-tree cursor   ~0.3 us   │
  │   - Deserialize row         ~0.2 us   │
  │   - Parse src_id string     ~0.1 us   │
  │   - Hash lookup for seq_num ~0.2 us   │
  │                                        │
  │ Per round: 200K x 0.8 us = 160 ms     │
  │ 30 rounds: 4,800 ms = 4.8 seconds     │
  └────────────────────────────────────────┘
DEEP DIVE -- Score Array Access 
  ISG uses a dense f32 array for scores:

  metrics.pagerank (or temp array during iteration)
  ┌───────┬───────┬───────┬───────┬───────┐
  │ E[0]  │ E[1]  │ E[2]  │ E[3]  │ E[4]  │ ...
  │ 0.002 │ 0.015 │ 0.001 │ 0.042 │ 0.003 │
  │  4B   │  4B   │  4B   │  4B   │  4B   │
  └───────┴───────┴───────┴───────┴───────┘

  scores[entity_42] = *(ptr + 42 * 4)
  O(1). 4 bytes. In L3 cache.

  50K entities x 4 bytes = 200 KiB
  The ENTIRE score array fits in L2 cache.

  SQLite equivalent:
  ┌─────────────────────────────────────┐
  │ HashMap<String, f64> scores;       │
  │                                     │
  │ scores["rust:fn:handle_request"]    │
  │   1. Hash string        ~20 ns     │
  │   2. Find bucket        ~10 ns     │
  │   3. Compare key string ~15 ns     │
  │   4. Random memory access          │
  │                                     │
  │ Per lookup: ~50 ns (vs 1 ns)       │
  │ Plus: HashMap is 3-5x larger in    │
  │ memory than a dense array          │
  └─────────────────────────────────────┘

PageRank on ISG: ~3 ms total (30 rounds). PageRank on SQLite: ~5 seconds. That's a 1600x difference. The secret: sequential scan + dense score arrays + CPU prefetch.

ISG Binary ~3 ms

PageRank (30 rounds, 50K/200K):
  Edge scan: 0.7 ms (sequential)
  Score updates: 1.5 ms (dense f32[])
  Convergence check: 0.2 ms
  Overhead: ~0 (no alloc)
  ─────────────────────
  Total: ~3 ms

SQLite ~5 sec

PageRank (30 rounds, 50K/200K):
  Edge cursor: 4800 ms (B-tree walk)
  Score lookup: 300 ms (HashMap)
  String hashing: 200 ms
  Row deser: 150 ms
  Allocations: ~6M mallocs
  ─────────────────────
  Total: ~5000 ms

Personalized PageRank (PPR) -- The Hot Path

Used for: "What's important relative to THIS entity?" Runs on every user click in the Parseltongue UI. Budget: 50 ms.

Access pattern: Like PageRank but starting from ONE seed node. Uses random walks or power iteration from the seed. Touches a SUBSET of the graph (the "neighborhood"). Mix of neighbor iteration (like BFS) and score accumulation (like PageRank).

ZOOMED OUT -- PPR From a Seed 
  Seed: entity 42 (user clicked "main()")

  Round 1: Push score from 42 to neighbors
  ┌─────────────────────────────────────────┐
  │          0.85                            │
  │  [42] ────────> split among neighbors   │
  │   |              [7]  gets 0.28         │
  │   |              [15] gets 0.28         │
  │   |              [88] gets 0.28         │
  │   +── 0.15 stays (teleport back to 42)  │
  └─────────────────────────────────────────┘

  Round 2: Push from 7, 15, 88 to THEIR neighbors
  (only entities with score > threshold)

  After 5-10 rounds: converged.
  Typical: touches ~500-2000 entities (not all 50K).

Why this is the hardest test: PPR mixes random access (jumping to arbitrary entities) with sequential access (reading their edge lists). It also has a hard latency budget (50 ms) because it runs interactively.

DEEP DIVE -- PPR Inner Loop on ISG 
  For each active entity with score > threshold:

  ISG version:
  ┌──────────────────────────────────────────┐
  │                                          │
  │ // O(1): read from dense array           │
  │ let score = scores[entity_seq];    ~1 ns │
  │ let out_deg = entities[entity_seq]       │
  │               .out_degree;         ~5 ns │
  │ let contrib = score * 0.85               │
  │             / out_deg as f32;      ~1 ns │
  │                                          │
  │ // Contiguous edge read                  │
  │ let off = fwd_off[entity_seq];     ~1 ns │
  │ let edges = &fwd[off.start..             │
  │              off.start+off.count]; ~1 ns │
  │                                          │
  │ for e in edges {                         │
  │   scores[e.dst_seq] += contrib;    ~1 ns │
  │ }                              each iter │
  │                                          │
  │ // Teleport                              │
  │ scores[seed] += score * 0.15;      ~1 ns │
  │                                          │
  │ Per entity: ~15 ns + 1 ns/edge           │
  └──────────────────────────────────────────┘

  SQLite version:
  ┌──────────────────────────────────────────┐
  │                                          │
  │ SELECT dst_id FROM edges                 │
  │ WHERE src_id = ?;                        │
  │                                          │
  │ Per entity: ~15 us (15,000 ns)           │
  │ Plus HashMap lookup for scores: ~50 ns   │
  │ Plus string hashing per edge: ~20 ns     │
  │                                          │
  │ 1000x slower per entity.                 │
  └──────────────────────────────────────────┘

PPR touching 1000 entities: ISG = ~0.2 ms. SQLite = ~200 ms. ISG easily fits in the 50ms interactive budget. SQLite needs aggressive pruning or precomputation to get close.

4
Leiden -- Community Detection

Used for: "Which entities belong together?" Finds natural clusters in your code graph (like "auth module entities" or "HTTP handler cluster").

Access pattern: The most demanding pattern. For each node, compute modularity gain of moving it to each neighbor's community. This means: for EACH node, read ALL its edges, and for EACH edge, look up the DESTINATION's current community. Random access + neighbor iteration + global metrics. Many iterations.

ZOOMED OUT -- Leiden Moves Nodes 
  Initial: every entity in its own community

  ┌─C0──┐  ┌─C1──┐  ┌─C2──┐  ┌─C3──┐
  │ E[0]│  │ E[1]│  │ E[2]│  │ E[3]│ ...
  └─────┘  └─────┘  └─────┘  └─────┘

  Iteration: try moving each entity to
  its neighbors' communities

  "Should E[2] move to C1?"
  ┌─────────────────────────────────────┐
  │ Check edges of E[2]:               │
  │   edge to E[1] (in C1) -- strong   │
  │   edge to E[5] (in C4) -- weak     │
  │                                     │
  │ Modularity gain for C1: +0.03      │
  │ Modularity gain for C4: +0.01      │
  │                                     │
  │ Best gain: C1. Move E[2] to C1.    │
  └─────────────────────────────────────┘

  After:
  ┌─C0──┐  ┌──C1───┐  ┌─C3──┐
  │ E[0]│  │E[1]E[2]│  │ E[3]│ ...
  └─────┘  └────────┘  └─────┘
DEEP DIVE -- Leiden's Data Appetite 
  For each entity (50K), Leiden needs:

  ISG access pattern:
  ┌─────────────────────────────────────────┐
  │ 1. Read entity's edges (contiguous)     │
  │    off = fwd_off[e]           ~1 ns     │
  │    edges = fwd[start..count]  ~5 ns     │
  │                                         │
  │ 2. For each edge, read dst community    │
  │    comm = community[edge.dst] ~1 ns     │
  │    (dense u16 array, entity N at N*2)   │
  │                                         │
  │ 3. Accumulate modularity per community  │
  │    community_weight[comm] += w  ~1 ns   │
  │                                         │
  │ 4. Read community totals                │
  │    comm_total[comm]           ~1 ns     │
  │    (another dense array)                │
  │                                         │
  │ All data: dense arrays. All in L3.      │
  │ Per entity: ~20 ns + edges * 3 ns       │
  └─────────────────────────────────────────┘

  SQLite access pattern:
  ┌─────────────────────────────────────────┐
  │ 1. Query edges:                         │
  │    SELECT * FROM edges WHERE src=?      │
  │    ~15 us per entity                    │
  │                                         │
  │ 2. For each edge, query community:      │
  │    SELECT community FROM entities       │
  │    WHERE id = ?                         │
  │    ~5 us per edge                       │
  │                                         │
  │ 3. Query community aggregates:          │
  │    SELECT sum(degree) FROM entities     │
  │    WHERE community = ?                  │
  │    ~10 us per community                 │
  │                                         │
  │ Per entity: ~15 us + edges * 5 us       │
  │ Plus N+1 query problem!                 │
  └─────────────────────────────────────────┘

Leiden typically runs 5-15 iterations over the full graph before converging. Each iteration visits every entity.

ISG Binary ~15 ms

Leiden (10 iterations, 50K/200K):
  Per iter: 50K entities x 20 ns
          + 200K edges x 3 ns
          = 1 ms + 0.6 ms = 1.6 ms
  10 iters: ~16 ms

  community[N] = u16 dense array
  100 KiB total. Fits in L2 cache.

SQLite ~75 sec

Leiden (10 iterations, 50K/200K):
  Per iter: 50K x 15 us (edge query)
          + 200K x 5 us (comm lookup)
          = 750 ms + 1000 ms = 1750 ms
  10 iters: ~17,500 ms

  Plus community UPDATE queries
  after each move: ~5 us each
  Total: ~75 seconds

Leiden on ISG: 15 ms. Leiden on SQLite: 75 seconds. The difference: 5000x. Community IDs as a dense u16[] array (100 KiB, fits in L2) vs. SQL UPDATE per community change.

5
k-core Decomposition -- Core/Periphery

Used for: "Which entities are in the core of the codebase (heavily connected) vs. periphery (loosely connected)?" Peels away low-degree nodes layer by layer.

Access pattern: Iterate all entities. Remove those with degree less than k. Recount degrees for remaining entities. Increase k. Repeat. Needs: degree lookup (dense array), neighbor iteration (edge lists), and a "removed" bitset.

ZOOMED OUT -- k-core Peeling 
  k=1: Remove entities with degree < 1
  ┌─────────────────────────────────┐
  │  Before:                        │

SCC -- Strongly Connected Components (Tarjan)

Used for: "Find all circular dependency cycles." If A calls B, B calls C, and C calls A, they form an SCC. Every entity in an SCC of size > 1 is part of a cycle.

Access pattern: DFS (depth-first search) through ALL nodes using forward edges, then DFS again using REVERSE edges. Needs: neighbor iteration in both directions + a stack + visited/lowlink arrays.

ZOOMED OUT -- Tarjan's Algorithm 
  The algorithm does TWO full DFS traversals:

  Pass 1: DFS using FORWARD edges (edges.fwd)
  ┌────────────────────────────────────────┐
  │ Visit every entity via outgoing edges  │
  │ Record "finish order" (when DFS backs  │
  │ out of a node)                         │
  │                                        │
  │ [42] ──> [7] ──> [3] ──> (dead end)  │
  │                    finish: 3, then 7   │
  │      ──> [15] ──> [42] (cycle!)       │
  │                    finish: 15           │
  │ finish: 42                             │
  └────────────────────────────────────────┘

  Pass 2: DFS using REVERSE edges (edges.rev)
  ┌────────────────────────────────────────┐
  │ Process entities in REVERSE finish     │
  │ order from Pass 1.                     │
  │ Each DFS tree = one SCC.              │
  │                                        │
  │ [42] <── [15] <── [42]  (SCC found!) │
  │ SCC = {42, 15}                         │
  └────────────────────────────────────────┘

The critical advantage of ISG: it has BOTH edges.fwd AND edges.rev. Forward edges sorted by source. Reverse edges sorted by destination. Both with O(1) offset lookup. This is exactly what SCC needs.

DEEP DIVE -- SCC Uses BOTH Edge Files 
  ISG has two edge files -- purpose-built for SCC:

  edges.fwd (sorted by src_seq):
  ┌───────────────────────────────────┐
  │ Entity 0's outgoing | E1's | E2's │
  │ [0->5, 0->8, 0->12]|[1->3]|...  │
  └───────────────────────────────────┘
  fwd_off[0] = {start: 0, count: 3}

  edges.rev (sorted by dst_seq):
  ┌───────────────────────────────────┐
  │ Entity 0's incoming | E1's | E2's │
  │ [5->0, 9->0]       |[0->1]|...  │
  └───────────────────────────────────┘
  rev_off[0] = {start: 0, count: 2}

  Pass 1 (forward DFS):
    "neighbors of 42" = fwd[fwd_off[42]..]
    Contiguous read. ~10 ns.

  Pass 2 (reverse DFS):
    "who points to 42" = rev[rev_off[42]..]
    ALSO contiguous read. ~10 ns.

Bonus: Why 64 Bytes = 1 Cache Line Matters

A CPU cache line is 64 bytes on all modern CPUs (x86 and ARM). This is the smallest unit the CPU can load from memory. By making each entity entry exactly 64 bytes, ISG ensures:

DEEP DIVE -- Cache Line Alignment 
  Entity entry = 64 bytes = 1 cache line

  When you read entity 42:
  ┌──────────────────────────────────┐
  │ CPU loads exactly 1 cache line   │
  │ from L3 (or RAM if cold).       │
  │                                  │
  │ That cache line contains:        │
  │ - name reference     (6 bytes)  │
  │ - kind + visibility  (2 bytes)  │
  │ - file path ref      (6 bytes)  │
  │ - line range         (4 bytes)  │
  │ - signature ref      (6 bytes)  │
  │ - pagerank           (4 bytes)  │
  │ - degrees            (4 bytes)  │
  │ - k_core + community (4 bytes)  │
  │ - fan_out start/count(6 bytes)  │
  │ - fan_in start/count (6 bytes)  │
  │ - id hash + ref      (10 bytes) │
  │ - padding            (6 bytes)  │
  │                                  │
  │ EVERYTHING about entity 42 in   │
  │ ONE memory load. No second read. │
  └──────────────────────────────────┘

  If the entry were 65+ bytes:
  ┌──────────────┬──────────────┐
  │ Cache Line 1 │ Cache Line 2 │
  │ (first 64B)  │ (last 1B)   │
  └──────────────┴──────────────┘
  TWO cache line reads for one entity.
  Doubles latency. Wastes 63 bytes of
  the second cache line.

  If the entry were 128 bytes:
  ┌──────────────┬──────────────┐
  │ Cache Line 1 │ Cache Line 2 │
  │ (first 64B)  │ (last 64B)  │
  └──────────────┴──────────────┘
  TWO cache lines. Half the entities
  fit in L3 cache (25K instead of 50K).
  For 50K entities, the index spills
  out of L3 and starts hitting RAM.
