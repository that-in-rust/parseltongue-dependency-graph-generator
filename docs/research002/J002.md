# Agent Context Query Tools

Source: classification pass over [`J001-what-next.md`](J001-what-next.md) on 2026-07-05, plus focused web and GitHub repository search on 2026-07-05 using terms around `MCP code graph`, `codebase context`, `tree-sitter MCP`, `codebase memory`, `GraphRAG`, `dependency graph`, `repo map`, `codebase indexer`, and `token reduction`.

Question:

> Which tools are about the loop: LLM asks a query to a tool; the tool responds with relevant context that helps the LLM decide better in the most efficient way, including dependency graph evidence for what the LLM should explore next with minimum tokens?

Working criteria:

- The tool exposes a query surface an agent can call: MCP, CLI, API, SDK, daemon, or similar.
- The response is selective context, not a full repository dump.
- The context is structured enough to guide the next step: graph, dependencies, references, repo map, blast radius, cycles, semantic index, or compact code memory.
- The strongest matches reduce token waste by telling the LLM which files, entities, paths, or relationships matter next.

### 1. Insight Observations

#### Premise Check

- The best unit of comparison is not stars, language count, or whether a repo says "MCP." The best unit is **tokens to confident next action**.
- Agents do not merely need retrieval. They need **decision surfaces**: what should I inspect, what can I safely edit, what breaks, what tests matter, what changed, what graph path connects these things, and what evidence proves this claim.
- A tool with one precise surface can be more valuable than a tool with thirty vague tools. But a broad tool wins when its broad surface is job-shaped, not primitive-shaped.
- README claims about token savings, accuracy, and benchmark ratios should be treated as vendor claims until independently benchmarked in this repo.
- The agent-arsenal answer should avoid tool sprawl. The winning stack is a small set of complementary surfaces: one structural graph engine, one semantic/lexical search layer, one change-safety/review layer, one memory/proof layer if long-running work matters, and one visual/onboarding layer when humans need to see the map.

#### Expert Lenses Used

- Agent operator: which surface actually changes what an agent does next?
- Product strategist: where is the repeated, high-frequency, high-pain job?
- Infrastructure engineer: which surfaces are operationally simple enough to keep installed?
- Skeptical reviewer: which repos overclaim, duplicate another layer, or create tool overload?

#### Working Thesis

For Parceltongue, the most valuable surfaces are **job-shaped graph queries**, not generic "code search." Search is necessary, but it is a layer. The real product wedge is an evidence router that can answer:

- "What is the minimal context to edit this safely?"
- "Who calls this, and who depends on the callers?"
- "What changed in this branch, and what is the blast radius?"
- "Which tests or flows are likely affected?"
- "Which dependency path connects A to B?"
- "Is this symbol or call chain real, or did the model hallucinate it?"

The strongest arsenal candidates are therefore not just the biggest repos. They are the repos that expose **agent verbs**: `impact`, `trace`, `context`, `detect_changes`, `review_context`, `tests_for`, `project_map`, `get_architecture`, `validate`, `blast_radius`, `find_path`, `minimal_context`, and `call_graph`.

My Shreyas-style take: start with a **narrow high-frequency workflow** rather than a grand "understand everything" promise. The wedge with the cleanest PMF is:

> "Before the agent edits, ask the graph for the smallest safe context and blast radius. After the edit, ask the graph what changed and which tests/flows are affected."

That is better than a generic repo chatbot because the user already has urgency at that moment. The cost of being wrong is concrete. The result can be measured. And it naturally becomes a habit.

### 2. Final Recommendation

I would not install every shiny MCP server. Tool sprawl hurts agents: too many overlapping descriptions, too many possible first moves, too much stale state. I would choose one tool per job.

Highest-signal stack to try first:

| Arsenal layer | Best Bullseye candidates | Why this layer matters |
| --- | --- | --- |
| Default structural graph engine | `codebase-memory-mcp`, `GitNexus`, `sdsrss/code-graph-mcp`, `tessera` | This is the main "what should I explore next?" surface. It should answer graph questions in one call and make the agent less dependent on grep/read loops. |
| Change-safety and review layer | `LegacyCodeHQ/clarity-cli`, `tirth8205/code-review-graph`, `n24q02m/better-code-review-graph`, `MikeRecognex/mcp-codebase-index` | This is the pre-commit / PR / refactor wedge. It is frequent, bounded, and measurable: fewer missed dependents, fewer blind reviews, fewer unnecessary file reads. |
| Semantic and structural search layer | `cocoindex-code`, `codemogger`, `probe`, `code-search`, `chunkhound` | This solves the "I know the concept but not the symbol" job. It is not enough by itself for safe edits, but it is essential for first contact and discovery. |
| Memory and proof layer | `claude-brain`, `atlasmemory`, `atrium` | This helps long-running agents preserve decisions, lessons, proof anchors, and context discipline across sessions. It is valuable after the graph/search layer is stable. |
| Human-visible onboarding layer | `Graphify`, `Understand-Anything`, `CodeGraphContext`, `GitNexus` | Humans still need confidence. Visual graphs, dashboards, and guided tours help a user trust the agent's mental model and spot surprising coupling. |

Recommended first stack:

1. **Primary graph engine:** try `codebase-memory-mcp`, `GitNexus`, `sdsrss/code-graph-mcp`, and `tessera` in a direct benchmark on this repo.
2. **Review/change safety:** keep `Clarity` or `code-review-graph` as a pre-commit companion. Clarity is simpler; code-review-graph is richer.
3. **Semantic search:** use `cocoindex-code`, `codemogger`, or `probe` only if the primary graph engine's search is weak. If the graph engine already has good search, do not add another search MCP by default.
4. **Memory/proof:** add `atlasmemory` or `claude-brain` only after the first three layers are working. Memory is valuable, but premature memory systems create rituals before the core retrieval loop is proven.
5. **Visual trust:** use `Graphify`, `Understand-Anything`, or `GitNexus` UI when onboarding a human or presenting architecture. Do not make visual graphing the default agent loop unless it feeds compact query results back to the agent.

Benchmark plan for choosing the primary graph engine:

| Benchmark task | Winning signal |
| --- | --- |
| "Find where smart context is built in this repo." | Fewest calls and smallest correct context pack. |
| "What changes if I edit the parser/indexing layer?" | Accurate direct and transitive dependents, no massive dump. |
| "Which tests or examples should run after this edit?" | Concrete test/file recommendations with evidence. |
| "Trace route/CLI command to implementation." | Correct call/path chain, not just keyword hits. |
| "Review current git diff." | Risk-ranked changed symbols, affected flows/tests, and bounded output. |
| "Validate whether a symbol mentioned by the LLM exists." | Deterministic yes/no with suggestions for near misses. |

The product lesson for Parceltongue:

- A generic graph is not enough. The agent needs **verbs**.
- A search result is not enough. The agent needs **next-step guidance**.
- A beautiful visualization is not enough. The agent needs **bounded evidence**.
- A memory store is not enough. The agent needs **proof that memory still matches code**.
- A big MCP surface is not enough. The agent needs **a small default playbook**.

The likely Parceltongue wedge should be phrased as:

> "Before editing, Parceltongue gives the agent the minimal safe context: relevant symbols, callers/callees, dependency path, affected tests, and risk-ranked blast radius. After editing, it verifies the diff against the graph."

That wedge is more PMF-shaped than "codebase graph for agents" because it lives exactly where the user feels pain: the moment before a blind edit and the moment after a risky change.
