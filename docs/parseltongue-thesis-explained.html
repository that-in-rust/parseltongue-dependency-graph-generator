Product Design Thesis

Parseltongue

A reading environment for code. Not another IDE. Graph-powered navigation. LLM-assisted comprehension. Like having a local guide in a foreign city.

"Grep returns files. Parseltongue returns understanding."
1
The Big Idea
ELI5 -- what Parseltongue is and why it exists
▼
The Metaphor

Parseltongue is Google Maps, but for code.

Right now, getting a new codebase is like being dropped in a foreign city with no map -- just a phone book (the file tree). You flip through 400 entries hoping to find something relevant.

before vs after 
  WITHOUT PARSELTONGUE              WITH PARSELTONGUE

  You, lost in a city:              You, with a map:

  +-----------------+              +-----------------------+
  | main.rs          |              |   [Auth]---[API]       |
  | config.rs        |              |     |    /   |         |
  | utils.rs         |              |   [DB]--[Models]       |
  | handler.rs       |              |                       |
  | service.rs       |   vs        |  You are here: [API]   |
  | mod.rs           |              |  "handles POST /users" |
  | types.rs         |              |  Read next: [Auth]     |
  | ... 392 more     |              +-----------------------+
  +-----------------+
     "where do I even start?"          "I see the whole picture"

Parseltongue gives you four things that a file tree never will:

🌎

Satellite View

Architecture map showing 8-15 "neighborhoods" (community clusters) so you see the shape of the whole system.

🔎

Street-Level View

Source code with clickable links to neighbors -- callers, callees, trait implementations.

🧑🎓

Local Guide

An LLM that sits beside you and explains what you're looking at. 2-3 sentences, not a lecture.

📖

Travel Journal

Reading history that remembers where you've been, suggests where to go next, and lets you resume.

The key insight: The app is for READING code, not writing it. Like a Kindle for codebases -- not an IDE.
▶ Why "reading" is the underserved use case
IDEs are built for writing code. They optimize for autocomplete, refactoring, debugging. But most engineering time is spent reading and understanding code someone else wrote. Studies show developers spend 58-70% of their time reading code, yet no tool is purpose-built for that. Parseltongue fills that gap: it treats a codebase as a structured book to be explored, not a file system to be edited.

The Three Layers of the System
Human layer -- LLM layer -- Engine layer
▼

The system is a three-layer sandwich. The top layer is what you see and click. The middle layer is the LLM that explains things. The bottom layer is the database and algorithms.

  │  │  Silent  │ │ Reactive │ │  Tour  │ │ Conf- │  │
  │  │ Annotat. │ │ Explain  │ │ Plnner │ │ usion │  │
  │  └──────────┘ └──────────┘ └────────┘ └───────┘  │

Critical rule: The LLM never blocks navigation. Source code appears instantly (~100ms). The LLM explanation arrives asynchronously (~2s). You never wait for AI to start reading.

This split is intentional. The source code is the primary reading surface. The LLM is a companion, not a gatekeeper. You can read perfectly well without it -- but it enriches the experience when it arrives.

Orientation Lenses -- "Where am I?"

Architecture Overview

Satellite view of the whole codebase as 8-15 community clusters. The first thing you see.

2

Breadcrumb trail + neighborhood graph showing exactly where you are right now.

3

Heat overlay showing structural importance via PageRank + in-degree + k-core.

Deep Reading Lenses -- "What does this do?"
4

Sorted entity list + source code + mini-map for one module at a time.

Vertical waterfall showing execution flow, 5 hops deep.

Split view connecting abstract traits to their concrete implementations.

Color-coded ownership/borrowing annotations. Syntactic only, honest about limits.

8
Guided Tour

Numbered chapter list generated by LLM from graph structure. With checkmarks for progress.

9
"What to Read Next?"

Personalized PageRank suggestions filtered by your reading history.

10
Dependency Ladder

Upstream/downstream tree centered on the entity you're currently viewing.

Compare & History -- "How do these relate?"
11
Side-by-Side Comparison

Structural diff of two entities: shared callers, unique traits, coupling.

12
Reading History & Bookmarks

Timeline + resume + coverage overlay showing what you've explored.

The Graph Algorithms
10 algorithms explained like you're 5
▼

Each algorithm does one job. Here is what it does and why Parseltongue needs it, explained with real-world metaphors.

Algorithm ELI5 Metaphor Powers
Leiden "Finding friend groups at a party" -- who talks to whom most Community clusters on the architecture map
PageRank "Who's the most popular kid" -- importance by who links to you Sorting entities by importance, hotspot detection
PPR "Who's important TO ME right now" -- importance relative to where I stand "What to read next?" suggestions
BFS "Ripples in a pond" -- explore outward from a drop, capped at 5 hops / 50 nodes Call chains, blast radius, neighborhoods
k-core "Peeling an onion" -- remove outer layers to find the dense core Core vs periphery overlay
SCC "Finding circular highways" -- groups where A→B→C→A Cycle detection (filter trivial size=1)
RRF "Asking 3 friends and combining their answers" -- fusion of FTS5 + trie + trigram Search results ranking
In/Out Degree "Counting incoming/outgoing phone calls" Fan-in/fan-out badges on source code
Betweenness "Finding the bridge everyone must cross" Bridge entity highlighting (precomputed)
Ego Network "Your immediate circle of friends" -- 1-hop neighbors around you Neighborhood mini-map, LLM context

The LLM's Personality
Not a chatbot. A senior engineer sitting next to you.
▼

The LLM is a reading companion, not a search engine. It behaves like a senior engineer who's already read the codebase and is sitting next to you, pointing things out.

the personality 
  ┌─────────────────────────────────────────┐
  │                                         │
  │       NOT THIS:          THIS:          │
  │                                         │
  │   A lecturer at      A colleague who   │
  │   a podium giving    leans over and    │
  │   a 30-min talk      says "look at    │
  │   you didn't ask     line 156, that's  │
  │   for                the key part"     │
  │                                         │
  └─────────────────────────────────────────┘
Good -- 2-3 sentences, specific, graph-aware
"This function handles both single and batch modes because it's called from two places -- the consumer loop and the batch flusher. Notice the match on line 156."
Bad -- 500 words, generic, lecture-style
"This function is responsible for processing messages in a streaming pipeline. In Rust, streaming is typically implemented using the Stream trait which provides an asynchronous iterator pattern. The poll_next method..."
The 150-word rule: Automatic explanations are capped at 150 words. The user must explicitly ask for more. Brevity is respect for attention.
▶ The 6 LLM behavior patterns
  1. Narrated Companion -- Auto-explains on navigation. 2-3 sentences: why it exists + what to notice. Triggers when you click to a new entity.
  2. Codebase Tutor -- "The streaming module has 3 key concepts. Let's start with MessageEnvelope..." Structured learning on request.
  3. Confusion Resolver -- Explains THIS specific Pin<Box<dyn Future>>, not a generic Rust tutorial. Context-specific help.
  4. "Ask Before Dump" -- Broad question? Ask which part. "Message delivery has 3 stages. Which one?" Never dumps everything at once.
  5. Next-Best-Reading -- "You just read Consumer::poll. Read ConsumerGroup::rebalance next because..." Graph-informed navigation aid.
  6. Compare Two Things -- Structural diff with graph data: "ConsumerGroup has 8 callers vs TopicConsumer's 2." Numbers, not opinions.

The Build Roadmap
Three phases from MVP to full experience
▼

Three versions, each delivering a complete, usable product. Each version answers a harder question.

v1.0

"I can browse this codebase"
  • Tauri app shell with drag-and-drop
  • Tree-sitter entity + edge extraction
  • SQLite schema
  • Architecture overview map (Leiden)
  • Community zoom with PageRank sort
  • Source pane with caller/callee chips
  • Breadcrumb trail
  • Neighborhood mini-map (ego, PPR)
  • Search bar (RRF: FTS5 + trie + trigram)
  • Hotspot overlay toggle

v1.1

"The app guides me"
  • LLM companion panel
  • Guided tour generation
  • "What to read next?" suggestions
  • Reading history + coverage overlay
  • Resume from last session
  • Bookmarks and pins

v1.2

"I understand Rust patterns"
  • Trait/impl browser
  • Call chain explorer
  • Side-by-side comparison
  • Cycle detection, dead code dimming
  • k-core overlay, dependency ladder
  • Confusion resolver LLM pattern

The Biggest Risks
9 failure modes and how to prevent each one
▼

Every product has ways it can fail. These are the 9 most dangerous ones, each with a specific mitigation built into the design.

⚠ "Wall of Text"

LLM talks too much. User ignores the companion panel entirely.

Fix: 150-word hard cap on auto-explanations

⚠ "Fake Map"

Leiden communities don't match real subsystems. Map misleads instead of helps.

Fix: modularity > 0.3 gate, fallback to folder tree

⚠ "Stale Graph"

Code changed but graph didn't update. User reads outdated structure.

Fix: file hash check + "stale" badge + one-click re-index

⚠ "Wrong Path"

Tree-sitter picks wrong call target. Edges point to the wrong function.

Fix: dashed lines for ambiguous edges, "3 possible targets" tooltip

⚠ "Boring Tour"

Tour starts with utility functions. User gets bored before reaching the good parts.

Fix: PageRank-prioritized entry points

⚠ "Info Overload"

500 nodes on first open. User is overwhelmed and closes the app.

Fix: community-level default (8-15 clusters), zoom is opt-in

⚠ "Meaningless Hotspot"

Logging module shows as #1 because everything calls it. Misleading signal.

Fix: exclude infrastructure entities from ranking

⚠ "Slow Navigation"

Every click waits for LLM. Navigation feels sluggish and frustrating.

Fix: async LLM, source renders instantly (~100ms)

⚠ "Reading Anxiety"

"15% complete" feels overwhelming. User feels they'll never finish.

Fix: frame as coverage ("explored 3 key subsystems") not completion

▶ Why "Fake Map" is the most dangerous risk 
  If Leiden produces bad clusters:

  ┌────────────────────┐  ┌─────────────────┐
  │ "Auth cluster"     │  │ "Data cluster"  │
  │                    │  │                 │
  │  login()           │  │  validate()     │
  │  parse_csv()  (?!) │  │  hash_pwd() (?!)│
  │  encrypt()         │  │  read_file()    │
  └────────────────────┘  └─────────────────┘
   parse_csv in Auth?        hash_pwd in Data?
   The map lies. Trust collapses.

  The fix: check modularity score.
  If modularity < 0.3, the communities
  are noise. Fall back to the folder tree
  (which is always honest).

The One-Sentence Thesis
The fundamental insight behind everything
▼
"Parseltongue is a reading environment that uses graph structure to turn a large codebase into something that feels like an explorable, guided, structured book -- where every page has context, every concept has neighbors, and a companion is ready to explain exactly what you need when you need it."

A search tool answers questions. A reading companion helps you FORM questions.

It shows you things you didn't know to ask about. It says "you've read the Consumer trait but not the ConsumerGroup that coordinates them -- that's probably why the ownership model seems confusing."

Architecture Overview → Community Zoom → Read Most Important Entity

From "I have no idea" to "I'm reading the most critical function" in 30 seconds.
