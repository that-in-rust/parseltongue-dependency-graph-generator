## 1. User Journeys

### Journey 01: Add Git Repo In Tauri

The first impression should feel local, simple, and trustworthy.

1. The user opens the Tauri app and sees a privacy-first welcome message:
   Parseltongue runs locally, does not send source code to a remote server, and exists to help the user and their LLM orient inside a repository.
2. The user clicks `Add Workspace` and selects a folder.
3. Tauri validates that the selected folder is a **git repo root**.
4. If the folder is not a git repo, the app rejects it immediately with a clear reason and no partial workspace creation.
5. If the folder is a git repo, Tauri scans for nested git repos and submodules inside it.
6. Nested repos are shown explicitly and marked **excluded from parent indexing by default**.
7. The parent repo becomes a valid workspace candidate.
8. Any nested repos are shown as separately addable future workspaces rather than being silently swallowed into the parent.

The user should leave this journey with one clear mental model:

> One workspace equals one git repo root.

### Journey 02: Index And Get URL

The second journey should feel like moving from raw code to a usable local service.

1. The user starts indexing from Tauri.
2. Tauri shows a progress stream with a visible state change from `Unindexed` to `Indexing`.
3. Indexing completes locally using the Rust-first, tree-sitter-only pipeline.
4. The workspace row updates with:
   - workspace name
   - freshness status
   - last indexed timestamp
   - basic counts
   - preferred local port
   - copyable HTTP URL
5. If this is the first successful index, the workspace is assigned a preferred local port.
6. Tauri shows the active HTTP URL as the handoff point for LLM use.

The outcome should feel like:

> I went from “I have code” to “my LLM has a local URL it can query.”

### Journey 03: Search To Map

The third journey is the product’s real center of gravity.

1. The user or LLM calls search.
2. `FFF` returns a small list of public-interface-centric candidates quickly.
3. Each result includes enough information to decide the next move:
   - interface label
   - kind
   - file-span hyperlink
   - lightweight aggregate counts
4. If the user wants deeper reading, they follow the file span directly.
5. If the user wants structural consequence, Parseltongue returns the relevant Interface Dependency Map slice.
6. Tauri renders a lightweight 2D Interface Dependency Map with basic motion and drag/reposition support.

The graph view is for orientation, not for becoming a complex graph IDE.

### Journey 04: Reindex And Reuse

The fourth journey should preserve trust over time.

1. The repo changes.
2. The workspace becomes `Stale`.
3. The user reindexes from Tauri.
4. Parseltongue tries to reuse the workspace’s preferred local port.
5. If that port is occupied, Parseltongue assigns a safe fallback port and updates the active URL.
6. Tauri refreshes freshness, counts, and the displayed URL.

The user should never wonder whether the shown URL or workspace state is outdated.

## 2. Product Thesis And Non-Goals

### Parseltongue Should Ship A Rust-First Interface Dependency Map Product

`v313` should help humans and LLMs land inside an unfamiliar repository and quickly understand the public dependency surface without reading the whole codebase or pretending to offer compiler-truth semantics.

The governing thought is:

> Parseltongue should feel like a local Rust-first orientation product, not a broad code intelligence platform.

### What v313 Must Be

- Rust-first
- tree-sitter only
- local-first
- workspace-driven
- graph-backed for walking and export
- small enough to explain in a few minutes

### What v313 Must Not Be

- not a full IDE
- not a generic graph browser
- not a rank-runtime product
- not a compiler-enriched truth engine
- not an OSS corpus platform
- not a multi-language-deep platform in this version

### Product Promise

`v313` succeeds if it can honestly answer:

- what public interfaces exist here?
- what is likely connected to this interface?
- what changes are affected one hop away?
- what changes are affected two hops away?
- where should I read next?

## 3. Tauri App Contract

### Tauri Is The Launcher, Control Plane, And Lightweight Visual Surface

Tauri is the local control room. It starts the workflows, shows status, and gives the user a small trustworthy graph preview. It is not the main reasoning engine and it is not the main reading surface.

### Tauri Owns

- adding and removing workspaces
- validating git repo roots
- detecting nested repos and submodules
- starting indexing and reindexing
- showing freshness and status
- showing preferred port and active HTTP URL
- copying the URL to the clipboard
- rendering a basic HTML/CSS/JS 2D Interface Dependency Map

### Tauri Does Not Own

- editing code
- storing or browsing raw source as a rich editor
- deep semantic exploration workflows
- a heavy architecture workbench
- the core search or walk logic itself

### Reliability And Security Posture

The Tauri layer should follow a reliability-first posture:

- use async commands for I/O-heavy operations
- return serializable error payloads
- keep command registration centralized
- stream indexing progress through events or channels
- use narrow filesystem permissions
- apply least-privilege path scope wherever possible

### Visual Scope

The graph visual is intentionally light:

- 2D only
- HTML/CSS/JS only
- simple motion only
- enough drag/reposition to orient the user
- no obligation to become a rich click-through graph studio in `v313`

## 4. Workspace And Git Rules

### Only Git Repo Roots Are Valid Workspaces

`v313` treats workspace identity as a git-root decision, not a loose folder choice.

### Workspace Rules

- only git repo roots are valid workspaces
- non-git folders are rejected before indexing starts
- nested git repos and submodules are detected during validation
- nested repos are excluded from parent indexing by default
- nested repos are shown as separately addable workspaces
- one workspace maps to one git root

### Port And URL Rules

Each successfully indexed workspace gets:

- a persisted preferred local port
- an active HTTP URL derived from the current bound port

Port behavior:

1. On first successful indexing, assign a preferred local port.
2. On future starts or reindexes, try to reuse that preferred port.
3. If the preferred port is occupied, bind to a safe fallback port.
4. Always show the actual active URL in Tauri.

### User-Visible Workspace States

- `Invalid workspace`
- `Nested repos detected`
- `Unindexed`
- `Indexing`
- `Fresh`
- `Stale`
- `Failed`

## 5. Search Model

### FFF Is The Front Door

`FFF` is the first meaningful step in the product.

Its job is simple:

- take a vague query
- return likely public-interface-centric candidates quickly
- give the user or LLM enough context to choose the next step

The line to preserve in the product story is:

> `FFF` finds the place; the Interface Dependency Map explains the place.

### Search Sequence

1. The user or LLM sends a query.
2. `FFF` returns a short candidate list.
3. Each candidate includes:
   - stable interface key
   - label
   - kind
   - file-span hyperlink
   - lightweight aggregate counts
4. The caller either:
   - follows the file span for deeper reading, or
   - requests one-hop or two-hop interface impact

### Explicit v313 Search Boundaries

- no separate interface-detail endpoint
- no giant “do everything” query endpoint
- no requirement to return raw source through the API
- no obligation to expose internal entities as first-class surfaced graph nodes

## 6. Data Model And Runtime Split

### v313 Should Use Two Layers, Not One Confused Graph

The product should be honest about what exists internally versus what is surfaced by default.

### Layer 01: SQL Metadata Layer

The SQL metadata layer holds the durable catalog and supporting structure:

- workspaces
- git roots
- preferred ports
- files
- folders
- Rust entities
- imports
- simple statements
- comments and tests
- word-count and count metadata
- aggregate counts and spans

This layer exists to support:

- indexing status
- search support
- file-span linking
- local summaries
- future drill-down potential

### Layer 02: Walk Runtime / Surfaced Map Layer

The surfaced Interface Dependency Map should stay deliberately readable.

Default surfaced node types:

- `folder`
- `file`
- `public_interface`

Default surfaced edge types:

- `contains`
- `depends_on`

This surfaced map supports:

- readable orientation
- one-hop interface impact
- two-hop interface impact
- export for humans and LLMs

### The Key Compromise

Imports and simple statements may exist in the metadata layer, but they are **not** part of the default surfaced Interface Dependency Map in `v313`.

That keeps the product honest in two directions:

- internally richer than the default export
- externally readable enough to use and explain

### Runtime Scope

`v313` uses a walk runtime only.

It does not include:

- PageRank
- HITS
- Katz
- eigenvector ranking
- cluster ranking
- a dedicated rank runtime

## 7. LLM-Callable API Surface

### The API Should Be Small Enough To Memorize

`v313` should expose only the following six endpoints.

| Endpoint | Purpose |
| --- | --- |
| `GET /server-health-check-status` | Confirm service liveness |
| `GET /codebase-statistics-overview-summary` | Return workspace summary, counts, freshness, preferred port, and URL |
| `GET /interface-dependency-search?q=...` | `FFF`-powered search with file-span hyperlinks and aggregate counts |
| `GET /one-hop-impact-interface-list?entity=...` | Return direct affected public interfaces |
| `GET /two-hop-impact-interface-list?entity=...` | Return two-hop affected public interfaces |
| `GET /interface-dependency-map-export?format=csv` | Export readable Interface Dependency Map CSV data |

### Search Response Expectations

`GET /interface-dependency-search?q=...` should return a short candidate packet, not a giant dump.

Each candidate should include enough to choose the next move:

- interface key
- label
- kind
- file path
- line span
- hyperlink-friendly file span
- lightweight aggregate counts

### Impact Response Expectations

`GET /one-hop-impact-interface-list?entity=...` returns direct affected public interfaces only.

`GET /two-hop-impact-interface-list?entity=...` returns the affected public interfaces within two hops only.

Both responses should stay interface-scoped and avoid turning into raw adjacency dumps.

### Explicit API Exclusions

- no interface-detail endpoint
- no rank endpoints
- no cluster/community endpoints
- no mega-query endpoint

## 8. Export Contract

### Runtime Storage And Export Format Must Be Separated

The internal runtime format may be optimized for storage and walking.

The export format must be readable by:

- humans
- LLMs
- lightweight frontend code

### Default Export Shape

The default export produces:

- `interface_nodes.csv`
- `interface_edges.csv`

This should behave like a readable node table plus an edge table, not a clever binary artifact.

Recommended node fields:

- `node_id`
- `node_type`
- `label`
- `parent_id`
- `file_path`
- `span`

Recommended edge fields:

- `from_id`
- `edge_type`
- `to_id`

### Default Export Semantics

Default surfaced node types:

- `folder`
- `file`
- `public_interface`

Default surfaced edge types:

- `contains`
- `depends_on`

### Explicit Export Boundary

Do **not** include imports or simple statements in the default `v313` Interface Dependency Map export.

Those may exist internally, but they are not part of the default surfaced map contract.

## 9. Trust, Failure States, And Acceptance

### Trust Boundaries

The product must be explicit about what it is and is not doing.

`v313` guarantees:

- Rust-first depth only
- tree-sitter-only extraction
- walk-runtime-only behavior
- no raw code persistence
- public-interface-scoped impact lists

`v313` does **not** guarantee:

- compiler truth
- full semantic resolution
- cross-language deep dependency truth
- rank-derived importance

### Failure States

The product must surface failure honestly:

- invalid workspace selection
- nested repos detected and excluded
- indexing failure
- stale workspace after repo changes
- preferred port unavailable and replaced by fallback
- missing or incomplete graph output for the current workspace

### Acceptance Criteria

The draft is only successful if `v313` clearly commits to all of the following:

1. Git repo validation works and is part of the product story.
2. Nested repos are excluded from parent indexing by default.
3. Indexing yields a preferred local port and copyable HTTP URL.
4. `FFF` is the search front door.
5. The LLM-facing API surface is the locked six-endpoint set.
6. One-hop and two-hop impact interface lists are supported.
7. The Interface Dependency Map export is readable as CSV.
8. Tauri can visualize the surfaced map in simple 2D.
9. The whole product can be demoed in a few minutes without explaining old architecture sprawl.

## Appendix A. Deferred Surface

The following items are explicitly deferred and should not leak back into `v313` scope:

- rank runtime
- interface-detail API
- internal-entity drilldown as a surfaced default
- statement-level surfaced APIs
- imports/statements in the default visual graph
- all-OSS corpus productization
- cross-language deep support
- snapshot diff and simulation workflows
- richer export standards such as JGF, DOT, Parquet, and SARIF

## Closing Position

`v313` should be remembered as the version where Parseltongue stopped trying to be everything and instead became easy to explain:

> a local Rust-first product that gives humans and LLMs a small trustworthy Interface Dependency Map, a copyable local URL, and a clear next step.
