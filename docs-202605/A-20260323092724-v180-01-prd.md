# v180-01 PRD

**Date**: 2026-03-23
**Status**: Draft
**Owner**: Parseltongue

---

## 1. One-Sentence Thesis

v180 turns Parseltongue into a more rigorous and truthful code graph system by removing CozoDB, keeping Turso/libsql as the durable store, making the runtime graph RAM-native, and preserving exhaustive file-span truth while keeping the HTTP API recognizable.

---

## 2. Why v180 Exists

The current product already computes graph algorithms in RAM after loading entities and edges from storage.

That means the core runtime truth is already:

```text
storage -> load rows -> build RAM graph -> run algorithms -> return JSON
```

v180 exists to make that reality explicit and clean.

The release is not about adding a new graph database.
It is about making the current system more rigorous, more truthful, and easier to evolve.

---

## 3. Product Goals

1. Remove CozoDB from the ingestion, storage, and serving path.
2. Keep Turso/libsql as the only durable local store.
3. Make the query-time graph explicitly RAM-native.
4. Preserve line spans as first-class identity for the current snapshot.
5. Persist exhaustive file-local span coverage for each indexed file.
6. Keep the existing HTTP API categories and paths recognizable.
7. Improve internal rigor without turning v180 into a graph database rewrite.

---

## 4. Product Non-Goals

v180 does not include:

1. A new general-purpose graph database.
2. A full public query-language redesign.
3. Architecture simulation as a shipped end-user feature.
4. A giant final taxonomy for every possible span kind.
5. Folder nodes mixed directly into the base graph.
6. New algorithm families as the headline of the release.
7. Breaking the existing HTTP route surface on purpose.

---

## 5. Core Product Decisions

### D1. CozoDB is removed

CozoDB is not part of the v180 target architecture.

It is removed from:
- ingestion
- durable storage
- server boot path
- graph query execution

### D2. Turso/libsql remains the durable store

The durable database is responsible for:
- codebase metadata
- indexed file metadata
- file hashes
- file-span truth
- entity rows
- edge rows
- FTS support
- restart durability

It is not the graph algorithm engine.

### D3. RAM is the active graph runtime

All graph traversal and analysis endpoints operate on an in-memory graph built from durable rows.

That RAM graph is the active source of truth for:
- callers
- callees
- blast radius
- SCC
- centrality
- clustering
- token-budget traversal

### D4. File change invalidates the full file

If a file changes, v180 does not try to preserve partial identity inside that file.

The model is:
1. detect file hash change
2. invalidate prior file rows
3. reparse the whole file
4. rebuild spans, entities, and edges for that file

### D5. Exact spans matter more than fake stability

For the live graph, the exact current snapshot matters more than pretending keys survive edits.

That means line spans are first-class.

### D6. One identity is not enough

v180 separates three identity lanes:

1. `entity_id`
- internal integer storage primary key

2. `span_key`
- public exact key for the current snapshot

3. `semantic locator`
- continuity metadata for later matching and reasoning

## 6. User-Visible Guarantees

1. The HTTP API remains recognizable.
2. Entities continue to resolve to exact file spans.
3. Query responses continue to be graph-oriented rather than raw SQL-oriented.
4. The system becomes more truthful about what exists in a file.
5. Storage/runtime cleanup does not force a new interaction model on existing users.

---

## 7. Functional Requirements

### REQ-V180-001.0: Cozo removal

**WHEN** Parseltongue ingests or serves a codebase
**THEN** the system SHALL not require CozoDB for storage or query execution
**AND** SHALL use Turso/libsql as the only durable backing store
**SHALL** compile and run without Cozo-specific runtime paths in the v180 target path

### REQ-V180-002.0: RAM-native graph execution

**WHEN** the HTTP server starts
**THEN** it SHALL load persisted rows from Turso/libsql
**AND** SHALL build an in-memory graph representation from those rows
**SHALL** execute traversal and graph-analysis endpoints against RAM rather than SQL joins

### REQ-V180-003.0: Exact span identity

**WHEN** an entity is returned by the HTTP API
**THEN** it SHALL include exact location identity using `file_path`, `start_line`, and `end_line`
**AND** SHALL expose a span-addressable public key for the current snapshot
**SHALL** allow callers to re-open the exact source region directly

### REQ-V180-004.0: Exhaustive file-span truth

**WHEN** a file is successfully indexed
**THEN** the system SHALL persist a complete non-overlapping line-span partition for that file
**AND** every source line in the current indexed snapshot SHALL belong to exactly one persisted span segment
**SHALL** rebuild that partition whenever the file is reparsed

### REQ-V180-005.0: File-level invalidation

**WHEN** a file hash changes
**THEN** the system SHALL invalidate all prior spans, entities, and edges sourced from that file
**AND** SHALL reparse the entire file before re-inserting durable rows
**SHALL NOT** attempt partial intra-file preservation in v180

### REQ-V180-006.0: HTTP compatibility

**WHEN** v180 ships
**THEN** existing top-level HTTP endpoint paths SHALL remain recognizable
**AND** existing endpoint categories SHALL remain intact
**SHALL** limit response-shape changes to fields needed for storage and identity cleanup

## 8. Release Scope Boundaries

### In scope

- CozoDB removal
- Turso/libsql durable-store cleanup
- RAM-native graph clarification and cleanup
- exact span-based public identity
- integer durable row identity
- exhaustive file-span truth layer
- file-level invalidation model
- compatibility-preserving handler adaptation

### Out of scope

- full architecture simulation productization
- materialized multi-level warehouse views as a shipped feature
- new graph algorithm families as a release driver
- radical endpoint redesign
- final continuity matching logic across edits

---

## 9. Acceptance Gates

v180 is acceptable only if all of the following are true:

1. No live CozoDB dependency remains in the active v180 path.
2. Turso/libsql is the sole durable store.
3. The server boots by loading rows and building the RAM graph.
4. Entities are addressable by exact current spans.
5. Indexed files have durable exhaustive span coverage.
6. File changes trigger full-file replacement behavior.
7. Existing HTTP routes remain usable without a new query model.
8. Docs and run instructions reflect the actual architecture.
